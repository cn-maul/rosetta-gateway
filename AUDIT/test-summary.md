## 0. 总体结论：**核心网关功能完整、可上线**

最核心的一条链路**在真实进程上端到端跑通**（Lead 亲自验证，非进程内模拟）：

```
真实 gateway.exe（隔离状态目录）
  → 引导设管理员密码 → 建普通用户 → 普通用户自助建 key
  → 建 provider/凭据/模型/路由
  → 数据面 POST /v1/chat/completions（带该 key）
  → 转发到独立的假上游进程
  → 返回内容 + usage 落库 + 余额扣减
```

**账目精确到微元**：一次流式调用 `cost_total = 0.000026 元`，
余额与余数合计 `0 + 26 微元 = 26 微元` —— 与报表**完全一致**，一分不差。

四个方向全部通过：**功能完整**（A）、**账目准确**（B）、**权限无越权**（C）、
**无资源泄漏**（D）。

## 1. 实测通过的核心能力

### 数据面（真实进程 + 进程内 E2E 双层验证）

| 能力 | 实测结果 |
|---|---|
| 非流式全链路 | 200、usage 落库、余额扣减 —— 扣款额与 `cost_total` 一致 |
| 流式全链路 | SSE 分片正确、`[DONE]` 正确、usage 落库 |
| 上游凭据隔离 | 上游收到的是 **provider 自己的 key**，不是用户的网关 key |
| 模型别名 | 响应 `model` 是**公开名**而非上游 `model_id` |
| 失败转移 | 链首死 → 自动切健康目标并 200；归因到**实际服务**的目标 |
| **已提交后不重试** | 流式写出 `PARTIAL` 后掐断 → 次目标调用 **0 次**、无重复输出 |
| 配额 | 用尽 → 429，且**不碰上游**（计数器证明） |
| 限速 | RPM 跨入口共享（换路径绕不过去） |
| 快照生效 | 改配置**不重启**立即生效（`AutoReload` 承诺成立） |
| 客户端断开 | 上游 ctx **842µs** 内观察到取消、资源释放 |

### 权限（195 次实测，**零越权**）

65 条路由 × 3 身份。关键点：

- **作用域用数字证明**而非字符串匹配：alice=250000 / bob=750000 / admin=1000000。
  admin 那组是关键对照 —— 证明隔离不是因为表里只有一个人。
- 跨用户写（PATCH/DELETE/recompute）全 404 + **查库确认零副作用**。
- 管理员四条边界全拦住，失败路径**零副作用**。
- **CSRF 无缺口**；限速阈值与常量一致；匿名请求不计入限速（历史 bug 已回归）。

### 计费（并发压测）

- 并发扣费：**总额精确**、不超扣、不为负。
- 余数机制：跨一分正确清零；1000 次极小金额**无精度损失**（微元整数累加）。
- 幂等：8 并发同 `request_id` → 落库 8 行、`cost_total` 合计 16 元，**实扣仅 2 元**。
- 两处 P0 修复在并发下依然成立。

### 性能（确认项）

- **无 goroutine 泄漏**：1000 次非流式 +0、500 次流式 +0、客户端断开 −3。
- **无连接泄漏**：300 请求 / 15 连接 = **20× 复用**。
- **无内存泄漏**：请求数 ×4 而驻留堆 ×0.93；长流峰值堆与流长度**无关**。
- **usage 队列零丢失**：1524 条全部落库。
- `maxConcurrentAttempts=4` **未误伤数据面**（64 并发零 429）。

## 2. 发现的问题（按严重度）

### [P1] 写池单连接把吞吐钉在落库速率上（性能）

**因果证据**（不是推断）：去掉「入队+落库」后吞吐 **931 → 36144 req/s（38.8×）**。
写池微基准：200 并发写只有串行的 **1.12×**（串行化点）。

- 现象：QPS 在 50 并发见顶（1536），200 并发仍只有 1778，而 P99 从 15.6ms 涨到 510ms。
- **请求不失败**（零错误）→ 不会告警，只表现为「越用越慢」，最容易被误判成上游慢。
- 根因是结构性的：`SetMaxOpenConns(1)` + 每成功请求一次 INSERT（SQLite 单写者）。

对本项目的目标场景（局域网小团队）数千 QPS 可能**远超需要**，故标 P1 而非 P0。
缓解方向（**未实施，需你决策**）：批量落库（单事务多行 INSERT）是最直接的一击。

### [P2] 上游返回畸形响应时网关报 500 且不可转移

**Lead 独立复现确认**：假上游回 `200 + 半截 JSON`，网关回 **500 `internal_error`**，
健康上游被调用 **0 次**。

一个「接受请求但返回垃圾」的上游（中转网关挂了、返回 HTML 错误页）**永远不会被换掉**，
且 500 把运维的注意力引向**网关自己**，而坏的是上游。修法有两种取舍（网关侧分类 vs SDK 侧加哨兵），
见 [test-datapath.md §7](test-datapath.md)。**未修，等你决策。**

### [P2] 欠费时余数被回滚丢弃，且注释描述了不存在的重试路径

**Lead 已核实并修掉注释**：`balance_dao.go` 的回滚会连带撤销余数累加，而原注释称
「由调用方重试时重新累加」—— 实测读了真实调用方（`usageRecorder.charge`）：
它拿到 `ErrInsufficientBalance` **只记日志就返回，没有任何重试**。那条路径不存在。

影响有限（真正丢的只是不足一分的零头），但**注释与实现不一致**会误导后来人。
已把注释改成如实描述，并写明「正确修法是调用方在欠费时也保留零头，属口径变更」。

### [P2] `YuanToMicros` 亚微元兜底是单边偏差

`micros < 1` 时一律向上记 1 微元。与 `YuanToCents` 的零均值舍入不同，**它单向累积**：
实测 10000 次 × 0.0000001 元 → 真实 0.1 分、实扣 1 分（放大 10 倍）。

**Lead 已把这个取舍写进注释**：仍选向上取整，因为「每次最多多收 1e-6 元」比
「消费永久消失且与『本来免费』同形」更可控；并注明若将来出现真正低于 1 微元/次的定价，
正确做法是下沉记账单位而非继续放大。

### [结构性风险] 白名单是前缀匹配，新端点会自动继承放行

`/admin/api/usage` 在白名单里 → 该子树下**未来新增的一切端点**都被网关层放行。
`/usage/by-user` 正是这样落进来的。**当前安全**（`by-user`/`prune` 都有 `requireAdmin`，
实测 403），但将来有人忘了写 → 静默越权且**不报错**。

建议方向（未改）：给白名单加「例外子路径」，或让这些端点在注册时显式套 `requireAdmin`。

### 关于那个 DATA RACE（值得单独说）

本会话**一直以为 `-race` 跑不了**（MinGW 路径含空格）。teammate 发现机器上还有
`C:\mingw64\bin\gcc.exe`（无空格），设 `CC` 即可跑。我验证了检测器**真的在工作**
（阳性对照：故意造的竞争被如实报出），然后全仓跑 —— **抓出一条竞争**：

```
WARNING: DATA RACE
  Write at ...: cooldown_race_test.go:93（测试的干扰函数）
  Previous write at ...: upstream.go:425（MarkCredentialCooldown）
```

**定性：这是测试侧的竞争，不是生产缺陷。** 我逐处核对了生产代码里对
`cred.CooldownUntil` / `cred.Status` 的**每一处**读写 —— 全在 `p.mu` 内，纪律是对的。
问题在测试的干扰函数用了自己的 `mu` 去写同一个字段，两个锁保护一个字段。

**但它必须修**：它让 `go test -race ./...` **永久变红**，真正的竞争会被淹没在噪音里
—— 一个永远红的检测器等于没有检测器。已改为走 `p.mu`（不影响原判据：干扰要种的窗口是
「生产已解锁、正把快照交给 store」那一段，此时生产不持锁）。

同类问题在隔壁用例（`RecoveryNotMisjudgedUnderConcurrentCooldown`）也有，一并修了。

**修后全仓 `-race` 干净通过**（14 包全 ok）。

## 4. 测试如何「说谎」——四位测试工程师各自踩到的坑

这一节的价值不低于 bug 清单：**每个坑都曾产出过错误的结论**。

| 坑 | 表象 | 真相 |
|---|---|---|
| `sync.Once` 误用（一个 Once 关两个 channel） | 报「断开没传播到上游」，像严重 bug | 生产 **842µs** 就传播了；是等待姿势错 |
| 异步副作用断言过早 | 报「失败调用漏账」 | `usageRecorder` 异步落库，请求返回 ≠ 副作用落地 |
| 余额用例定价与余额不相称 | 报「费用被少扣」 | 单价 2000 元而余额 100 元，扣费**正确地**拒绝了 |
| 「+492 goroutine」像泄漏 | 报内存泄漏 | 是 transport 空闲连接池；真泄漏随**请求数**增长，而它随**并发数**封顶 |
| 连接 open=18 ≠ 0 | 报「连接未释放」 | 那是设计好的 keep-alive 池；正确判据是复用率 20× |
| 按「逐条按分求和」断言 | 报余额对不上 | 反证了真实链路走**微元累加**（按分求和会全舍成 0） |

**共同教训**：**先量时序 / 先建立正确判据，再下结论。** 否则会把「我的断言写错了」
写成「生产的 bug」—— 而那比漏测更糟，因为它会消耗信任。
这也是为什么本轮所有报告都有「未能验证的部分」一节：
**诚实说出没覆盖什么，比假装全覆盖有价值。**

## 5. 未能验证的部分（诚实清单）

1. **`/v1/responses` 入口零动态覆盖**（协议翻译的第三套 codec）。
2. **凭据冷却 / 熔断 half-open 探测名额未做 E2E** —— 只有单元级覆盖，
   而那正是历史上出过微妙问题的地方。
3. **畸形响应的流式路径只测了非流式**，流式「推测行为一致」—— 那是推测不是实测。
4. **百万行首剪的持锁时长未构造**，`busy_timeout=5000` 是否被撞破未排除。
5. **「不 Close 重开」≠ SIGKILL 强杀** —— WAL 崩溃恢复需子进程 + `taskkill` 脚手架。
6. **慢泄漏（小时级）不在覆盖范围**。
7. **真实上游行为未测** —— 所有数字来自回环假上游，描述的是网关自身开销。
8. **>12 核扩展性未测**。
9. **一次未复现的全仓失败**：某次 `./...` 报 `FAIL cmd/gateway`（用例名被截断），
   此后连跑 9 次全绿。判为间歇性 flake，位置在 `cmd/gateway`，如实记录未定位。

**`-race` 现已可跑并全绿**（见 §3），这一条从上轮的限制变成了已覆盖项。
