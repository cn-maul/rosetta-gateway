## 任务 1：访问密钥页加「按用户筛选」+「按用量降序」

**改动文件：** `web/src/views/Keys.vue`

### 做了什么

纯前端实现，**没有新后端接口**（`AccessKey` 已有 `username`，`used_tokens` 本来就在列表里）。

1. **筛选下拉**（`:110-207`, 模板 `:494-513`）
   - 值域是 **user_id**（不是 username）：username 可改名，拿名字当主键会让筛选在改名后静默失配。
   - 选项来自 `api.users()`（与 `UsersGroups.vue:112` 同款用法），**惰性加载** + 失败不阻塞列表。
   - 除了用户清单，额外补两类「用户清单里没有、但确实持有 key」的归属：
     - `user_id` 非空但用户已从库里消失 → 补一项 `xxx（用户已不存在）`，让这行始终可筛到；
     - `user_id` 为空（无归属 key）→ 用独立哨兵 `ORPHAN_FILTER = '\u0000orphan'`
       （`:145-153`）单独一项「无归属（不可用）」，且只在 `hasOrphanKeys` 为真时出现
       （`:160`）。
     - 理由：否则这些行在任何筛选下都不出现，用户会把「看不见」读成「不存在」。

2. **按 `used_tokens` 降序 + 稳定排序**（`:193-221`）
   - 排序放在 `visibleKeys` computed 里（`:209`），`slice()` 后再排，**不原地改 `keys`**
     （`recomputeUsage` 会就地改 `used_tokens`，原地排会让顺序依赖「用户点过哪些重算按钮」的历史）。
   - **稳定排序**：主键 `used_tokens` 降序；相等时用 `created_at` 升序、再用 `id` 升序兜底。
     `id` 是后端不变主键，保证顺序唯一且确定，两次渲染不会跳行。
   - 表头 `用量` 加 `↓` 标注方向（`:543`），筛选行常驻 `共 N / M 把 · 按用量降序`（`:512`,
     CSS `:756-763`）。

3. **筛选与排序共存**
   - 筛选只决定「看谁的行」，排序恒定生效；`visibleKeys` 先筛后排，二者独立。

4. **普通用户的权限差异处理（选了哪种：隐藏 + 不发请求）**
   - `/admin/api/users` 是 admin-only，普通用户调它只会吃 403；且他们的列表本来就只有自己的
     key（后端 `key_handler.List` 对非管理员强制按 `user_id` 收窄），「按用户筛」对他们恒等于
     「全部用户」。给一个只有自己一个选项的下拉是纯噪音。
   - 所以：下拉整块 `v-if="isAdmin()"` 隐藏（`:494`），`ensureUserOptions()` 里首行
     `if (!isAdmin()) return`，**普通用户连请求都不发**。详见 `:119-143` 注释。

5. **筛选后空态**：新增 `filteredEmpty`（`:224`），把「筛不出」与「本来就没有 key」分成两句话，
   否则用户会把「这个人的 key 在别的用户名下」读成「他一把都没有」。

### 判断 / 取舍
- 布局/写法贴 `History.vue` 的 `.filters`（flex + wrap + 10px gap），并在 Keys.vue 的 scoped
  style 里复用了 `.w-auto` / `.filters`，保证两张表的筛选区视觉一致。
- 没有把排序做成下拉里的一个选项：用户要的是「按用量降序」这个**恒定**行为，且筛选与排序常在
  同一次排查里同时用，所以让排序独立生效。

## 任务 2：管理员「认领 key」入口 —— 判断

**结论：前端本来就没有这个入口，无需删除。只修正了两处已经过时的注释。**

核查依据（都在前端、我没有改后端逻辑）：

1. `api.updateKey()`（`web/src/api.ts:492-515`）的 PATCH 载荷类型里**根本没有 `user_id` 字段**
   —— 只有 `name/enabled/quota_tokens/rpm_limit/tpm_limit/allowed_models/expires_at/
   allowed_ips/group_id`。
2. `api.createKey()`（`api.ts:466-491`）虽然**声明**了 `user_id?`，但注释和后端 `key_handler.Create`
   都明确：Create 一律忽略这个字段、强制 `owner = 调用者自己`。Keys.vue 的 `submitCreate`
   （`:290-303`）也**从来没有**传过 `user_id`。
3. Keys.vue 的编辑弹窗（`:687-739`）里**没有**归属字段；表格「归属用户」列（`:560-566`）
   是**纯展示**（`k.username || k.user_id` / 无归属徽章），不是可点的下拉。
4. 全仓 grep `user_id|Reassign|认领`：Keys.vue 里的命中全是我本次新增的筛选代码 + 两处
   只读展示 + 新建弹窗那个 `disabled` 的「归属用户」回显。

**所以**：管理员想改一把 key 的归属，前端从来没有提供过路径。用户的诉求「修掉认领给自己」
在前端侧**无对应物可修**——没有需要删除的按钮/下拉/字段。按指示「如果没有，就不要改」，
我没有为了「做出一个改动」而硬加再删。

**唯一改动（注释修正，不是功能改动）：** Keys.vue 里有两处注释在**描述一个不存在的功能**，
属于会误导后续维护者的陈述性缺陷，已改对：
- `:620-623` 新建弹窗上方原注释写「要替别人建，建好后在列表里**编辑归属**（仅管理员可改）」
  —— 编辑归属这个功能不存在，已改为如实说明「归属不是可选字段，界面上不给任何改归属的
  入口……归属只能通过那条 admin-only 的认领路径改变，前端从不暴露它」。
- `:21-26` `meName` 的注释原写「不再拉 /users：归属不再可选」—— 表述含糊，容易被读成
  「以前能选」，已改为明确说明 Create 忽略 `user_id`、PATCH 载荷里也没有 `user_id`。

**关于「普通用户之间转移」要不要保留的判断（虽然前端本来就没这个功能，但给出结论供后端参考）：**
不建议保留普通用户转移。理由：key 归属决定「谁付账、谁受限」——归属变更会把一把受管理员
收紧（配额/白名单/有效期/IP/禁用）的 key 整体换到另一个用户名下，等于让 A 的 token 记到 B 头上、
B 的分组/配额约束去套一把为 A 配置的 key。归属应当**只能由管理员单向调整**，且当前后端已经
只给 admin-only 的认领路径，前端不暴露是对的，保持即可。**前端不做任何改动。**

  无消费方。

  `v-else`，见 `:830`）。

### `api.audit()` 的去留：**保留**（决定 + 理由）

- **核查**：改动后全仓 grep `audit|Audit`，`api.audit()` 的唯一消费方就是被删的设置页。
  `AuditEntry` 类型现在也只被 `api.ts` 自己引用（`types.ts` 里保留定义，无人 import）。
- **决定：不删 `api.audit()`，也不删 `AuditEntry` 类型。** 理由：
  1. 任务要求「后端端点 `GET /admin/api/audit` 不要动」；前端 API 封装是这个端点唯一的
     类型化出口。把它删掉，等于前端**永久失去**用管理会话读审计的能力，将来想加回来得
     重写一遍类型与请求。
  2. 审计是安全/取证的正路（谁改了什么），删 UI 不等于这个能力该消失；`api.ts` 保留一个
     零成本的封装（不引用不打包业务代码）代价极低。
  3. `AuditEntry` 类型同理：它是后端 `audit_log` 响应的契约描述，留着无害，且未来任何
     审计相关界面（哪怕是只读的、或者挪到别的页）都能直接复用。
- 在 Settings.vue `:17-19`（`type TabKey` 上方）留了注释说明「删的是界面那一块，不是能力本身；
  端点与 api.audit() 保留」，防止后人看到零消费方就顺手删掉、导致前后端契约割裂。
