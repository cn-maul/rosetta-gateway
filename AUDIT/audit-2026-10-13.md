## 1. 架构与数据面（正确性）

### 1.1 请求主链路 ✅

`cmd/gateway/main.go:handleIngress` 的顺序经过精心设计，注释逐条论证：

```
鉴权 → RPM → 用户配额 → 解码 → TPM 预占 → Key 配额预占
  → 路由解析 → 模型白名单 → 请求总预算 → 余额预检
  → 故障转移循环 → 落库 → 扣费
```

**值得肯定的设计**：

1. **管理员在数据面被彻底拦截**（`internal/auth/auth.go`）。判定落在 `Authenticate` 而非 `handleIngress`，因此 `/v1` 三个推理端点、`/v1/models`、`/dashboard/billing/*`、`/v1/organization/*` **同时生效**。这是正确的收敛点——若在 handler 里加检查，其余入口会各自漂移。

2. **`committed ≠ success` 的区分**（`attemptOutcome`）。断流/溢出/客户端中断都是 `committed=true`（字节已写出，不能回退）但 `success=false`（必须让熔断与凭据冷却照常累计）。少了这个区分，"先 200 再断流"这种最常见的上游故障会让目标永不熔断。

3. **SSE 头推迟到首个事件之后才写**。这是故障转移能成立的前提：写出字节前失败可安全换目标。注释还解释了为什么**不能**给 `ChatStream` 套带超时的子 context（SDK 内部 `WithCancel` 后直传 `http.Do`，取消会掐断正在输出的长流）——这是实测结论，不是推测。

4. **`outcomeFromErr` 对流式哨兵的改判**（2026-10-10 P1）。`MapUpstreamError` 把 `ErrStreamTruncated` 映射成 `(200,"","")`，那个前提只在**已提交**时成立；未提交路径照搬会让客户端拿到 `HTTP 200 + 空响应`，且 `FailoverEligible` 返回 false 使故障转移链直接 break——**一个本该被链吸收的失败被伪造成成功**。修法是正确的：改判放在调用点，不动 `MapUpstreamError` 服务于已提交路径的语义。

5. **`totalRequestBudget`**（2026-10-10 P2）。单跳超时 × 故障转移目标数可以让客户端挂住约 5 分钟，期间占住下游连接、上游连接、配额预占行、故障转移槽位。病在上游、症状却在网关自己身上。由现有配置推导而非新增开关，避免了"调完设置还要记得同步另一个总开关"的跨字段隐性依赖。

### 1.2 故障转移与熔断 ✅

`internal/upstream/upstream.go` 的 half-open 探测名额管理有一个极易写错的配对关系，代码处理得很干净：

- `ClaimTargetProbe` 在**真的要发请求前**领取（提前领取会让被预算裁掉的目标永久占住名额）；
- 名额有两条出路：记账释放（`Record*`），或没走到记账时由 `ReleaseTargetProbe` 显式归还；
- 已记账的绝不能再还——`halfOpen` 是共享 bool 而非计数，重复归还会错清并发请求刚领到的名额。

`pool.SetCooldownStore(db)` 也值得点出：冷却状态落库，否则任何 admin 写操作触发的池重建都会把刚被判坏的凭据立刻放回轮换。

### 1.3 关停路径 ✅

`main()` 的关停顺序经过三轮修正，当前形态正确：

```
close(shutdown) → 等剪枝(5s上限) → 等重算(2s上限)
  → srv.Shutdown(10s) → srv.Close()（掐在途连接）
  → usage.wait(5s) → 退出
```

关键点：
- `usage.wait` **返回 bool**，false 时打 ERROR（"records were lost during shutdown"）。原实现静默 return，日志一片祥和、实际最多 50 条用量凭空消失，用户因此免单且配额被放宽。
- `usageRecorder.mu` 把"判 closed + 发送"变成原子操作。原来的 `select { case ch <- rec: default: }` 对**已关闭**的 channel 并不安全——向关闭的 channel 发送是 panic，不是走 default。触发时序是正常时序（Shutdown 到点只返回错误、不杀 handler），不是边角。

## 2. 安全

### 2.1 认证与会话 ✅

- **users 表是唯一身份来源**。并行的 `admin_token` / `admin_auth.json` 通道已删除，且 `csrf_test.go` 保留了 `/admin/api/password/set`、`/admin/api/password/check` 的断言路径——万一有人手滑加回 `publicAdminMux`，立刻红。这是好哨兵。
- **JWT**：显式 `WithValidMethods([]string{HS256})` + keyfunc 内二次校验 `SigningMethodHMAC`，堵住 `alg: none` 与 RS256/HS256 混淆。还冗余校验 `c.Subject == c.UserID`。
- **`auth_version` 栅栏**：改密码/禁用/改角色后旧 token 立即作废，不依赖进程内黑名单。
- **PBKDF2 210k 迭代**，恒定时间比较，格式化错误与密码错误不区分（无 oracle）。
- **`FailureThrottle`** 有三处细节做对了：无凭据请求**不计入**失败限速（否则任何 IP 连发 10 个匿名请求就能让 NAT 后面的所有人被锁 1 分钟）；冷却判定用 `until` 是否为零值而非 `!time.Now().Before(until)`（后者对新条目恒为真，计数永远涨不到阈值）；`Allow` 先占用并发额度再放行（否则同 IP 的 N 个并发会把 CPU 放大 N 倍）。

### 2.2 管理面权限收敛 ✅（有历史遗留，见 P1-2）

- `userAccessibleRoutes` 从**前缀白名单**改成**精确路由模式**（`PATCH /admin/api/keys/{id}`），新增端点默认 fail-closed。这个改动很关键：前缀匹配会自动放行该子树下未来新增的一切端点，实测踩到过 `/admin/api/usage/by-user` 被静默放行。
- `callerScope`（usage_handler）与 `requireAdmin` 双道防线。
- `denyAdminKeyCreate` 在路由层拦管理员建 key，且身份缺失一律 401（fail-closed）。

### 2.3 密钥与加密 ✅

- `master.key` 原子写（tmp → fsync → rename → fsync 目录），空文件/格式非法一律报错而非静默重生成——重生成会让库里全部凭据永久不可解。

### 2.5 🔴 P0-1：管理面写操作缺少 CSRF 令牌，且存在绕过 Content-Type 防线的端点

**这是本次审计唯一的 P0。**

**现有防线**（两道，均不完备）：

1. `decodeJSON` 强制 `Content-Type: application/json`（`helpers.go:100`）。这挡住了 `text/plain` / `application/x-www-form-urlencoded` / `multipart/form-data` 这类 **CORS safelisted** 的简单请求——浏览器发它们不触发预检。
2. `BootstrapSetup` 额外做 `server.SameOrigin(r)` 判定。

**缺口**：同源判定是 `sameOrigin()`（`server.go:161`）：

```go
func sameOrigin(r *http.Request) bool {
	if site := r.Header.Get("Sec-Fetch-Site"); site != "" {
		return site == "same-origin" || site == "none"
	}
	origin := r.Header.Get("Origin")
	if origin == "" {
		return true
	}
	...
}
```

它**没有被 `UserAuthMiddleware` 调用**。全仓确认：`SameOrigin` 的**唯一**调用点是 `user_handler.go:468`（BootstrapSetup）。因此除引导端点外，`/admin/api/` 下的所有写操作（建/改/删 key、改路由、改设置、导入配置、`config-export`）都没有同源校验。

**为什么 Content-Type 断言挡不住 `application/json`**：

#### 缺口一：存在完全绕过 Content-Type 防线的写端点

防线 1 **依附在 `decodeJSON` 内部**——只有"读 JSON body"的端点才受它保护。以下管理员写端点**从不解析 body**，因此完全不经过 Content-Type 断言：

| 端点 | 参数来源 | 后果 |
|---|---|---|
| `POST /admin/api/usage/prune` | URL query `?keep_days=N` | **不可逆删除用量明细**。且缺省用硬编码 30 天（见 P2-4），攻击者不带任何参数即可触发 |
| `POST /admin/api/keys/{id}/recompute-usage` | 路径参数 | 重算 key 用量（低危害，但证明该形态可达） |
| `POST /admin/api/logout` | 无参数 | 强制管理员登出（骚扰） |

跨站调用 `prune` 只需：

```js
fetch('http://gw:8666/admin/api/usage/prune', {
  method: 'POST',
  credentials: 'include',
  headers: {'Content-Type': 'text/plain'}   // safelisted → 不触发预检
})
```

`text/plain` 在 CORS safelist 内，**不触发预检**；handler 从不调 `decodeJSON`，防线 1 完全不适用。

#### 缺口二：受保护端点的防线依赖两条未测的隐式假设

对**解析 body** 的端点（建/改/删 key、改路由、改设置、导入配置、`config-export`），攻击者必须发 `application/json`，而不在 safelist 内的 Content-Type 会**触发预检**。此时防线成立依赖：

- **假设 A**：管理面不返回 CORS 头。我写了探针实测确认：

  ```
  OPTIONS /admin/api/keys       status=200  ACAO=""   ← 无 CORS 头，预检失败，浏览器拒绝
  OPTIONS /v1/chat/completions  status=204  ACAO="*"  ← 数据面按设计放行
  ```

  当前成立，但**是隐式的**：`CORS` 中间件靠 `strings.HasPrefix(r.URL.Path, "/admin")` 排除。将来任何人加一条"方便调试"的 CORS 规则（极常见的运维需求，而本项目 `/v1` 就有开 `*` 的先例），防线立刻失效。

- **假设 B**：全仓**没有任何测试**覆盖 `/admin` 的 CORS 头。已确认 `grep -rln "Access-Control-Allow-Origin" --include="*_test.go"` 返回空——假设 A 一旦被破坏，CI 全绿。

#### 实际可利用性（诚实评估）

会话 cookie 是 `SameSite=Strict`（`user_auth.go` 的 `SetSessionCookie`），这挡住了**跨站**场景。防线剩余的缺口是：

- **同站不同源**：网关在 `gw.corp.example.com`、攻击者控制 `evil.corp.example.com`（同一注册域下的子域）——`SameSite` 按 site 判定，**cookie 会被发送**。企业内网 DNS 常在同一父域下，这是现实场景。
- **旧浏览器**：不识别 `SameSite` 的老版本按无限制处理。
- **IP 直接访问**：局域网常见 `http://192.168.1.10:8666`，`SameSite` 对 IP 主机的 site 判定行为与域名不同。

（`sessionToken()` 还支持 `Authorization: Bearer`，该头非 safelisted，跨站带它会触发预检，因此**不是**额外敞口。）

**结论**：当前状态是"靠 `SameSite=Strict` + 两道隐式假设侥幸成立"，而非"有一道显式的 CSRF 防线"。OWASP 的标准做法（双提交 cookie / 同步器令牌）不依赖 Content-Type、不依赖 CORS 配置、也不依赖 SameSite，是独立的第三道防线。

**建议修复**（约 40 行）：

1. 登录后由 `SetSessionCookie` 额外写一个**非 HttpOnly** 的 `rosetta_csrf` cookie（随机 32 字节，base64）。
2. `UserAuthMiddleware.ServeHTTP` 在注入身份**之前**，对所有写方法（`POST/PATCH/PUT/DELETE`）校验：请求头 `X-CSRF-Token` 的值必须 `subtle.ConstantTimeCompare` 等于该 cookie 的值。

   **必须在 `AdminGateGuard` 之前、且不区分端点是否解析 body** —— 这正是覆盖 `prune` / `recompute-usage` / `logout` 那类的关键。
3. 失败一律 403 + 记 WARN（带 `request_id` 与 `remote`）。
4. `BootstrapSetup` 保留 `SameOrigin` 作为引导窗口的额外防线（那一步没有会话可绑，只能靠同源）。
5. **顺带补一条回归测试**：断言 `OPTIONS /admin/api/*` 的响应**不含** `Access-Control-Allow-Origin`（把上文"假设 A"从隐式变成显式）。当前全仓无此测试。

配套测试：`internal/server/csrf_token_test.go`，断言"无头 → 403"、"错值 → 403"、"有 Cookie 无头 → 403"（第三条形正是**同站攻击**，必测）。

**中期**：把不解析 body 的写端点改成走 `decodeJSON`（哪怕 body 为空），让 Content-Type 断言成为**所有**写端点的统一门禁，而不是只属于"恰好要读 body"的那些。

### 2.6 🟠 P1-1（安全/正确性）：用户级配额预检无预占，并发下可超发

`cmd/gateway/main.go:1580`：

```go
if u := snapshot.Get().UsersByID[authCtx.UserID]; u != nil && u.QuotaTokens > 0 {
    used, uerr := db.SumUserUsedTokens(r.Context(), authCtx.UserID)
    ...
    } else if used >= u.QuotaTokens { ... 429 ... }
}
```

这是纯粹的 **check-then-act**：读 `used` → 比较 → 放行。并发下 N 个请求读到同一个 `used` 并**全部通过**。

**这正是 Key 级配额在 2026-10-07 修掉的 P0-1 的同形缺陷**。Key 级的修法（`ReserveQuota`）是把"检查"与"占用"合并进同一条写事务，靠 SQLite 写锁串行化，预占落在独立的 `reserved_tokens` 列。用户级**没有对应的 `ReserveUserQuota`**。

注释里写着"与 key 级同口径：查询抖动时 fail-open"——fail-open 的**抖动策略**本身没问题（那是可用性取舍），问题是**并发语义**：fail-open 的前提是"至多一个在途请求超发"，而那只在串行时成立。

**后果**：`users.quota_tokens` 是三级配额的**最外层总闸**（MULTIUSER.md §4.3）。总闸在并发下可被超发，意味着给普通用户配的硬天花板不是硬的。而 `key_handler.Create` 的自助建 key 额度封顶逻辑依赖"用户级 quota 是硬天花板"这个前提——注释里明确写着"残留的真实敞口是用户级 quota 未设（0）时可以自铸不限额凭证，这由部署侧兜"。总闸不硬，那个兜底就漏了。

**建议修复**：照 `ReserveQuota` 的形态加 `ReserveUserQuota`（`user_usage_totals` 表加 `reserved_tokens` 列，或复用现成的窄表模式），在 `rateCommit` 里一并收尾。注意与现有 `rate.quotaReserved` 共用同一个 `rateCommit` 收尾——**分开放两次收尾只会让两边在某条路径上被漏掉一处，且配额那条漏掉是终身偏差**（这条纪律 `rateCommit.commit` 的注释已经写明了，照做即可）。

### 2.7 🟠 P1-2：审计 `actor` 恒为 `"admin"`

`cmd/gateway/main.go:470`：

```go
audit := func(method, path string, status int, remote, fields string) {
    entry := &store.AuditEntry{
        Ts: ..., Actor: "admin", Remote: remote, ...
    }
}
```

代码注释自己承认了："actor 写死 "admin" 是已知的不精确……普通用户对自己资源的写操作也会落 "admin" 记录"。

**为什么这是 P1 而不是 P2**：`userAccessibleRoutes` 已开放给普通用户的写端点有 5 个（`POST /admin/api/keys`、`PATCH /admin/api/keys/{id}`、`DELETE /admin/api/keys/{id}`、`POST /admin/api/keys/{id}/recompute-usage`、`POST /admin/api/me/password`）。也就是说**审计日志现在无法回答"这把 key 是谁建的"**——而这正是审计存在的唯一理由。安全事件回溯时，一条 `actor=admin` 的记录指向的是所有人，等于没有指向。

**修复成本极低**：`AutoReload` 的 `WriteAuditor` 签名加一个 actor 参数（或从 `r.Context()` 里用 `server.UserFromContext` 取，中间件已经注入了）。`autoreload.go` 里 `audit(r.Method, p, status, clientIP(r), auditFields)` 这一行的调用点加一个参数即可。`bootstrap` 路径（免鉴权）保留 `"bootstrap"` 字面量。

### 2.8 🟠 P1-3：引导窗口 + 非回环监听 = 远程抢注管理员

`main.go` 已经做了能做的告警：

```go
} else if pending != nil && !isLoopbackListen(cfg.Listen) {
    logger.Error("SECURITY: admin password not yet set AND listening on a non-loopback address — ...")
}
```

`isLoopbackListen` 还很仔细（解析失败保守返回 false、空 host = 全接口 = false、`net.ParseIP` 后 `IsLoopback()`）。

**但 Docker 镜像的默认配置就是 `0.0.0.0:8666`**（`docker/config.default.json`）。也就是说：

```
docker run -d -p 8666:8666 ghcr.io/cn-maul/rosetta-gateway:latest
```

**开箱即处于"任何能连到 8666 端口的人都能成为第一个管理员"的状态**。启动日志里有一条 ERROR，但容器部署的典型流程是 `docker run` 之后去开浏览器，没人看 `docker logs`。而攻击窗口是**永久的**——直到有人完成首次设置。

README 的推荐命令恰好就是上面这条。这是"默认不安全"的形态。

**建议**（三选一，按成本递增）：
1. **最低成本**：`docker/config.default.json` 改回 `127.0.0.1:8666`，DOCKER.md 明确写"要局域网访问需手动改 listen，并**先完成首次设置密码**"。（推荐先做这个）
2. 加一次性引导令牌：启动时生成随机 token 打到 stdout 并写入 `<home>/bootstrap_token`，`POST /admin/api/bootstrap` 必须携带它。窗口外的人拿不到。
3. 引导窗口加时间盒（如启动后 30 分钟自动关闭，此时只能靠 CLI 子命令建管理员）。

### 2.9 🟠 P1-4：流式响应提交后无输出流控

`attemptStream` 在写出 SSE 头之后进入事件循环，`consume` 直接 `sink.Event(ev)`。没有对**下游写出速率**做任何约束。

风险场景：上游是高速模型（几百 token/s），下游是慢客户端（移动网络、或客户端读取阻塞）。`sink` 内部有锁，`net/http` 的 bufio 缓冲会吸收一部分，但持续背压会让内存无界增长——每个在途流都占着一份缓冲。

**为什么现在没爆**：`totalRequestBudget` 封住了总时长（30s~30min），所以单个流的总量有界；局域网部署下游通常很快。

**为什么仍应修**：`stream_idle_timeout` 是**上游空闲**看门狗（默认 60s），它检测的是"上游不发"，不是"下游不收"。下游卡死时上游一直在发，看门狗永不触发，只有总预算兜底。而总预算最大 30 分钟——30 分钟 × 若干并发流，足以让单进程网关 OOM。

**建议**：给 `stream.Event()` 的消费加一个"上游读取节流"——下游写阻塞时暂停 `stream.Next()`。最简单的形态是把 `consume` 的写改成带超时的通道传递，或在 `sink` 里加写超时后主动 `stream.Close()` 并按 `truncated` 收尾（复用现有的断流路径，语义已经完备）。

## 3. P2 级发现

### 3.1 P2-1：`estimateBalanceCost` 与 `store.priceUsage` 是两份计价实现

`billing.go` 的 `estimateBalanceCost` 自己实现了三项计价公式，注释说明了原因（`priceUsage` 是包私有的，热路径在 `cmd/gateway` 层）并警告"两处若漂移，后果比不预检更糟：用户会在明明够钱时被拒"。

**问题**：这个警告是注释，不是机制。两处公式当前一致（我都核对过：都是 `uncached*pin + cached*phit + out*pout`，都是 `/1e6`），但没有任何测试钉住它们相等。

**建议**：把 `priceUsage` 导出为 `store.PriceUsage`，`estimateBalanceCost` 直接调用。删掉一份实现比维护"两处必须同步"的纪律可靠得多。

### 3.2 P2-2：`rand.Read` 返回值在多处被丢弃

```go
internal/crypto/crypto.go:251        rand.Read(b)                    // GenerateKey
internal/admin/provider_handler.go:484  rand.Read(b)                 // generateID
internal/server/server.go:31         rand.Read(b)                    // generateRequestID
internal/store/route_target_dao.go:128  _, _ = rand.Read(b)          // 显式丢弃
internal/store/topup_dao.go:110      _, _ = rand.Read(b)             // 显式丢弃
```

`crypto/rand.Read` 保证不返回 `io.ErrUnexpectedEOF`，实践中不会失败，所以**不是可利用的漏洞**。但 `generateID()` 用于 `usage_records.id`（主键）与 `balance_charges` 的幂等键——若熵源失败返回全零，会撞主键。`crypto.GenerateKey()` 用于 API key 生成，更不该静默。

`crypto.go` 的 nonce 生成本身用了 `io.ReadFull` 并检查错误（`crypto.go:214`），说明作者知道要检查——只是 `GenerateKey` 漏了。

**建议**：统一改成 `if _, err := rand.Read(b); err != nil { return "", fmt.Errorf(...) }`。约 5 处，都是一行改动。

### 3.3 P2-3：`orgCostsScope` 的管理员分支不可达

`billing.go:194`：`if authCtx.IsAdminOwner() { return "" }`（不限作用域 = 看全量）。但 `auth.Authenticate` 已经把管理员全部拒在 `ErrAdminCannotCallModel`，所以 `/v1/organization/*` 上**永远不会有管理员请求**——这个分支是死代码。

代码注释解释了保留理由（`balanceExempt` 的注释也解释了同样的纵深防御逻辑），但**这个场景与 `balanceExempt` 不同**：`balanceExempt` 防的是"扣错钱"（资金正确性），而 `orgCostsScope` 这里是"看得到全量费用"（信息泄露）。纵深防御在**收紧**方向上有价值，在**放宽**方向上没有——留着它意味着"万一鉴权被绕过，这条路径会自动给出全量数据"，那是把兜底写反了。

**建议**：删掉 `IsAdminOwner()` 分支，永远返回 `authCtx.UserID`。若确有运维需要看全量 org 费用，那属于控制面语义，应走 `/admin/api/usage`（已有 `callerScope` 处理）。

### 3.4 P2-4：`Prune` 端点的 `keep_days` 用 `store.DefaultRetentionDays` 而非配置值

`usage_handler.go:808`：`keepDays := store.DefaultRetentionDays`（硬编码 30）。

而配置里已经有了 `cfg.UsageRetentionDays`（可配 1..3650），定时剪枝用的就是它。手工 `POST /admin/api/usage/prune` 不带 `keep_days` 时会按 **30** 剪，而不是按运维配的值。

**后果**：运维把 `usage_retention_days` 配成 90（想留更久），某天手点了"立即归档"，明细被按 30 天剪掉——**不可逆，且与配置意图相反**。

**与 P0 的叠加**：这个端点恰好也是 P0-1 里"不解析 body、绕过 Content-Type 防线"的那个端点，且**不带参数即以默认值触发不可逆删除**。两个缺陷叠加后，一次成功的跨站请求就能删掉运维本想保留的 60 天明细。

**建议**：`UsageHandler` 构造时注入 `cfg`（`NewUsageHandler(db, cfg)`），`keepDays` 缺省取 `cfg.UsageRetentionDays`。注意这是**收紧方向**的隐患（剪太多），比剪太少严重。

### 3.5 P2-5：`user_usage_totals` 孤儿行不清理

`user_usage_totals` 由 `trg_update_user_usage_totals` 维护，`ON CONFLICT DO UPDATE` 累加。用户被删除时该行不会消失（`users` 与 `user_usage_totals` 之间没有外键）。

不是内存/磁盘问题（一行一个用户）。是**语义**问题：`SumUserUsedTokens` 对该用户仍返回历史累计值，而用户已不存在。目前没有路径会读到它（用户删除后其 key 也失效），所以是"将来的坑"而非当下的 bug。

**建议**：`DeleteUser` 时一并 `DELETE FROM user_usage_totals WHERE user_id = ?`。或接受现状并在注释里写明（本项目的注释纪律允许这种做法，但得写）。

### 3.6 P2-6：`dayExpr` 依赖进程时区，多时区部署无解

`dayExpr = strftime('%Y-%m-%d', ts/1000, 'unixepoch', 'localtime')`，时区由 `ApplyTimezone` 在启动时一次性设定（`TZ` 环境变量 + `time.Local`）。`internal/config/timezone.go` 的注释把 Windows/Linux 差异讲得很清楚（Linux 走 C 的 `tzset`，不看 `time.Local`），修法正确。

**残留限制**：这是**进程级全局**设置。一个网关服务跨时区的多个用户时，所有人的"按天"口径都用同一个日界。注释里没提这个限制。

**建议**：在 DOCKER.md / MULTIUSER.md 里写一句"按天统计的日界是全局的，跨时区团队请选择一个人为日界"。属于文档补全，不改代码。

### 3.7 P2-7：`Cache-Control: no-cache` 用于 SPA 入口

`webHandler` 对 `index.html` 设 `no-cache`（允许缓存但强制回源校验），对 `/assets/*` 设 `immutable`（文件名带内容 hash，正确）。`theme-init.js` 也是 `no-cache`（文件名不带 hash，正确）。

`no-cache` 是对的选择（`no-store` 会牺牲 bfcache），但**缺少 `ETag` 或 `Last-Modified`**，于是每次回源都是 200 + 全量 body，而不是 304。管理面是低频访问，影响很小。

**建议**：`index.html` 加一个基于内容 hash 的 `ETag`。低优先级。

### 3.8 P2-8：`AdminGateGuard` 对 `routes == nil` 静默降级

```go
if routes != nil {
    if _, pattern := routes.Handler(r); userAccessibleRoutes[pattern] { ... }
}
writeAdminErr(w, http.StatusForbidden, "需要管理员权限")
```

`routes == nil` 时**所有普通用户请求一律 403**（fail-closed，方向正确）。但没有日志——生产里 `routes` 由 `main.go` 传入恒非空，所以这条路径只在测试中出现。

**建议**：`routes == nil` 时加一条 `slog.Error("AdminGateGuard: routes table is nil; failing closed")`。fail-closed 的分支必须有可观测性，否则"为什么所有用户都 403"无从排查。这与本项目"失败必须留痕"的一贯纪律一致。

## 4. 值得肯定的工程实践（作为基线保留）

这些不是"没发现问题"，而是**明确做对了、且未来重构时不该退化**的部分。列出来是因为它们的价值容易被后来的"清理"误删。

1. **纵深防御的注释都写明了"为什么它现在不可达"**。`balanceExempt`、`orgCostsScope`、管理员短路——每一处都解释了"数据面上不可达，但保留作纵深防御"。这让后人不会把它当死代码删掉。

2. **每一条 fail-open / fail-closed 的选择都有论证**。余额预检 fail-closed（钱，漏放=白送，无兜底），配额预检 fail-open（token，有硬上限，下次预检挡住）。注释明确写着"请勿'统一'成 fail-open"。

3. **剪枝不变式由机制保证，不靠纪律**。`prune_batch` 临时表让"聚合"与"删除"共用**严格同一批 rowid**，从而"进了表 A 的必然被删掉"。注释记录了旧实现的缺陷（聚合无界、删除有界 → 同一批行被聚合两次 → 归档数字凭空变大 33%，不报错不告警，只有对账能发现）。还有一条：`ORDER BY ts` 而非 `ORDER BY id`——因为 `generateID()` 是纯随机 hex，不含时间成分，旧注释声称的"id 含时间前缀"是假的。

4. **`cost_pending` 把"免单"变成可查询状态**。查价失败不再只是打一条 WARN 然后永久免单，而是标记状态 + 后台每 5 分钟自动重算。这是从"无观测性"到"有观测性"的实质改进。

5. **`SetCredentialCooldown` 落库**。池重建不会把刚判坏的凭据放回轮换——这种"跨组件的状态该放哪"的判断，很多项目会做错。

6. **配置校验挡住了所有会 panic 的脏值**。负值超时（`time.NewTicker(-500µs)` panic，而此刻 SSE 头已写出不可撤）、回绕的超大毫秒数（`time.Duration(ms) * time.Millisecond` 在 `ms > 9.223e12` 时变负数）、`max_request_body_bytes` 上界 512MiB（inwire 三条入口都是 `io.ReadAll`，MaxBytesReader 是唯一闸门）。每一条都附带了"为什么这个上界是这个数"。

7. **`WriteTimeout: 0` 且解释了为什么**。net/http 的写超时从"开始写响应"起算覆盖整个响应时长，套上去会把正常吐字的流式响应硬切。流的生命周期已由 TTFT/空闲看门狗约束。这种"故意不设某个常见保护"的决策，配上了完整的反例论证。

8. **测试命名直接指向历史事故**。`TestCostPending_能被自动重算纠正`、`TestPrune_StatsUnchangedAcrossPrune`、`TestSessionGate_BearerTokenIsNotAnAdminCredential`——看测试名就知道它在防什么。
