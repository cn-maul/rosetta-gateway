# 性能审计报告 —— rosetta-gateway

- **日期**：2026-10-11
- **基线**：HEAD `cbffbc4` + 本轮 effort 修复；版本 1.5.3，rosetta SDK v1.1.1
- **生产负载**：约 4200 请求/天、950M token/天（≈0.049 req/s）
- **方法**：静态审计 + 一次性探针实测（探针已删，结论写进本报告）

---

## 一、结论先行

**当前生产负载下，网关没有任何性能问题。** 0.049 req/s 距离任何瓶颈都有 4~5 个数量级的余量。

真正值得关注的是**增长风险**——哪一项会先撞上墙。经实测，两条候选 P0 的结论是：

| 审计初判 | 实测结果 | 修正后定级 |
|---|---|---|
| SQLite 单写连接 ≈ 300~400 req/s 天花板 | **实测 21000 tx/s（单并发）～18700 tx/s（64 并发）**，折算约 6000~7000 req/s | ❌ **推翻**，降为 P3 |
| 用户配额 SUM 单用户 150 万行 ≈ 50~150ms | **实测约 0.5µs/行**：10 万行 51ms → 150 万行约 **770ms** | ⚠️ **确认，且比估的严重 5~15 倍** → 升为 P0 |

**唯一的 P0 是用户级配额预检**，而它的风险不在"会不会慢"，而在"剪枝是否真的在跑"。

## 二、实测数据

### 2.1 写事务吞吐（推翻静态推断）

`store.go:42` 把写池设为 `SetMaxOpenConns(1)`，静态审计据此推断这是"第一个会撞上的天花板"。**实测否定了这个推断**：

| 并发 | 事务数 | 耗时 | 吞吐 | 折算请求 |
|---|---|---|---|---|
| 串行（无竞争） | 300 | 13ms | **23832 tx/s**（42µs/事务） | ~7900 req/s |
| conc=1 | 100 | 5ms | 21043 tx/s | 7014 req/s |
| conc=4 | 400 | 22ms | 18273 tx/s | 6091 req/s |
| conc=16 | 1600 | 92ms | 17300 tx/s | 5766 req/s |
| conc=64 | 6400 | 342ms | 18731 tx/s | 6243 req/s |

**64 并发相比单并发只衰减 11%** —— 基本平坦。

**为什么比静态推断高两个数量级**：WAL 模式 + `_synchronous=NORMAL`（`store.go:34`）意味着提交**不 fsync**，只是把页写进 WAL 缓冲区。静态审计用的 2.7ms/事务 来自代码注释里的**旧口径**，那个数字包含了 fsync 成本。

> **这个配置的代价要说清楚**：`synchronous=NORMAL` 在 **WAL 模式下**只在**操作系统崩溃/断电**时可能丢事务（进程崩溃不丢）。如果生产环境有掉电风险且要求零丢失，应改回 FULL——但那会把吞吐打回 fsync 的量级（约 300~400 tx/s），也就是静态审计原来的估算。

### 2.2 用户级配额预检的增长曲线（确认并修正）

`SumUserUsedTokens` 在 `usage_records` 上做全量 SUM（`user_dao.go:379`），走 `idx_usage_user_ts`。

| 行数 | 单次耗时 | 折算 |
|---|---|---|
| 1,000 | 480µs | — |
| 10,000 | 4.8ms | — |
| 100,000 | **51.3ms** | 已超过流式首字预算（默认 30s？不，30s 是秒，但已占满 P99 预算） |

**约 0.5µs/行，完美线性。** 按生产速率外推：

| 时间跨度 | 该用户累计行数 | 单次耗时 |
|---|---|---|
| 3 个月 | ~38 万 | ~190ms |
| 1 年 | ~150 万 | **~770ms** |
| 2 年 | ~300 万（若无剪枝） | ~1.5s |

**修正说明**：静态审计估"150 万行 ≈ 50~150ms"，实测曲线外推是 **~770ms**，低了 5~15 倍。差异来源是审计用了"走索引应该很快"的直觉估计，没实测。

**关键缓解机制**：剪枝（`usage_archive.go`）会把过期明细聚合进 `usage_daily_rollups`，走 `idx_rollup_user(user_id)`，代价降到 O(归档天数)。所以：

> **这一项的真实风险 = 「剪枝是否真的在跑、keepDays 设了多少」。**
> 剪枝正常 → 明细窗口内行数有上限（如 30 天 × 4200 = 12.6 万行 ≈ 63ms）。
> 剪枝失效/未配 → 线性劣化到 770ms+。

**这是本报告唯一需要运维侧确认的事项**，见 §五。

### 2.3 现有性能测试的结论（可信）

| 项 | 实测 | 判定 |
|---|---|---|
| 上游连接复用 | 300 请求建 17 条连接 = **17.6×** | ✅ 良好 |
| 内存增长 | 请求数 ×4 → 堆增量 ×1.05 | ✅ **无泄漏** |

## 四、值得肯定的设计（避免误改）

这几条是本项目**做对了**的地方，任何优化方案都不应该动它们：

1. **快照用 `atomic.Pointer` 而非 `RWMutex`**（`snapshot.go:238`）——读路径**零锁**，重建不阻塞数据面。这是关键决策：静态审计最初假设存在 RWMutex 读争用，核验后发现不存在。
2. **数据面无 N+1**，快照重建是 10 次全量查询而非按实体循环，复杂度 `O(P+M+R+T+U+K)`，**无笛卡尔积**。
3. **触发器维护派生值**（`used_tokens` / `usage_totals`）——这是 P0 那条的**现成解法**，模式已存在，照搬即可。
4. **批量落库 + 逐条计价**（`main.go:2688`）——既省事务又不破坏"扣的 = 报表的"不变量。批量大小 50 是实测调过的（bs=200 反而回升）。
5. **读写分池 + WAL**（`store.go:40-55`）——写 1 连接、读 4 连接，方向正确。
6. **白名单刻意用线性扫描而非 map**（`auth.go:48-50`）——白名单个位数长度，避免每请求分配。**这是正确的取舍**，不要"优化"成 map。
7. **key 鉴权用 SHA-256 map 索引 O(1)**，且已正确论证不构成可用侧信道。
8. **`synchronous=NORMAL` 在 WAL 下**——正确的吞吐/耐久权衡（代价见 §2.1）。

## 五、P0 的实际严重性（已定位，无需你确认）

**我找到了决定性事实**：`DefaultRetentionDays = 30`（`internal/store/usage_archive.go:35`），且**硬编码、无配置项**——源码注释明确写「保留期是**唯一**的默认值来源，不进配置」。

所以 P0 的严重性可以从「推算」变成「算」：

| 场景 | 明细行数 | 单次 SUM 耗时 |
|---|---|---|
| 全部用户均匀（4200/天 × 30 天） | 12.6 万 | **~63ms** |
| 单用户占 50%（1800 req/天 × 30 天） | 5.4 万 | **~27ms** |
| 剪枝失效（累积 1 年） | 150 万 | **~770ms** |

**修正后的结论**——P0 的性质变了：

- **剪枝正常时**：最坏 ~63ms/次，落在**每个**启用用户级配额的请求上。0.049 req/s 下完全无感，但会给每个请求的 P99 加约 63ms，流式请求的 TTFT 会被推高。
- **剪枝失效时**：770ms/次，才是真正的灾难。

也就是说这不是「剪枝是否在跑」的不确定性，而是 **「63ms 的常驻税」+「剪枝一旦失效就劣化 12 倍」**。

### 建议做的两件事

**1. 让保留期可配置**

`DefaultRetentionDays = 30` 硬编码意味着：
- 用量小的部署：**多留 30 天明细纯属浪费**（每行还要维护 5 个索引）
- 用量大的部署：**30 天可能不够**，需要能调到 7 天

改法很小：`internal/config/config.go` 加 `usage_retention_days` 字段（带上下界校验，参考同文件其它字段写法），`cmd/gateway/main.go:611` 改用它。

**2. 给 `users` 加 `used_tokens` 触发器（消除 63ms 常驻税）**

`access_keys` 已有 `trg_update_used_tokens` 触发器维护 `used_tokens`。给 `users` 加一个同构的，**63ms 直接归零**——因为触发器在批量落库的同一事务里已经逐行更新了（`usage_archive.go:143-149`），加一个几乎不增加写成本。

**前提说明**：`usage_records.user_id` 是**冻结列**（`usage_dao.go` 注释明确说明这是为处理 key 删除而设计的），所以触发器同样能正确累加，**语义不会从「实时」退化成「延迟」**。

### ✅ 实施记录（2026-10-11，本节两条建议已落地）

| 项 | 落地方式 |
|---|---|
| 保留期可配置 | 新增 `config.UsageRetentionDays`（JSON `usage_retention_days`，1~3650，缺省 30），`main.go` 剪枝改用它；`config.example.json` 与 `docker/config.default.json` 同步 |
| 消除 63ms 常驻税 | 新增窄表 `user_usage_totals(user_id, total_tokens)` + 触发器 `trg_update_user_usage_totals`；剪枝事务内同步回收；`SumUserUsedTokens` 改读该表 |

#### 关键设计决策：为什么是独立窄表，而不是 `users.used_tokens` 列

第一版直接给 `users` 加了 `used_tokens` 触发器，**被现有迁移测试打回**：

```
TestMigration_BalanceColumnDefaultsExistingUsersToUnlimited
  error in trigger trg_update_user_used_tokens: no such table: main.users
```

根因是 SQLite（3.25+）在 `ALTER TABLE ... RENAME` 时会**校验并重写所有引用该表的触发器**。`ensureColumns` 里正有「重建 users 表补列」的逻辑，于是「users 上挂了引用它的触发器」会把**整个重建操作卡死** —— 而这是网关启动期的必经路径。

同一脆弱性也潜伏在既有的 `trg_update_used_tokens`（引用 `access_keys`）上：只是目前没有重建 `access_keys` 的代码路径，所以从未暴露。

**独立窄表彻底避开这个问题**：`user_usage_totals` 窄、只由迁移创建、不参与任何 `DROP TABLE`/`RENAME`，因此不会成为任何 schema 操作的绊脚石。代价是配额判定读数时一次主键查找（可忽略）。

`users.used_tokens` 保留为**展示字段**（由 `RecomputeUserUsage` 与回填同步维护），配额判定改读窄表 —— 展示值可以偶尔滞后，判定值不行。

#### 配对不变量（已由测试钉住）

触发器只在 `INSERT` 时加，剪枝负责减。两者缺一，该值就是**单向虚高**：剪掉的量永久留在计数里，配额因此低估已用量 → 用户可超额使用，而界面数字看起来完全正常。

`internal/store/user_used_tokens_test.go` 覆盖：

- 剪枝后累加值仍等于「明细 + 归档」真实合计（同时覆盖回收生效与口径没跑偏）
- 空串 `user_id`（孤儿 key 历史行）不被累加
- 回填一次性且幂等（marker 语义）
- 用户不存在时返回 0 + nil，不返回 `ErrNoRows`

> **踩过的坑（留给下一个改这里的人）**：
> 1. `UsageSource` 是 `UNION ALL` 复合 SELECT，其内部**自带别名 `u`**；外面再套一层 `(...) t` 会让 `u.` 前缀失效，回填静默返回全 0 且不报错。正确写法是引用其**输出列名**（`total_tokens` / `user_id`，取自 `usageSourceDetailCols`）。
> 2. SQLite 的 `INSERT ... VALUES ... WHERE` 与 `INSERT ... SELECT ... WHERE` 都是**语法错误** —— `WHERE` 只能跟在 `FROM` 之后。触发器里要用 `INSERT ... SELECT ... WHERE` 形式。
> 3. 测试里 `Open()` 时 migrate **已经**跑过一次回填并写下 marker，要模拟「老库升级」必须先 `DELETE FROM app_settings WHERE key = ...`。

### 验证剪枝是否真在跑（一条 SQL）

```sql
-- 明细窗口应 ≈ 30 天；若远大于，说明剪枝没生效
SELECT COUNT(*),
       MIN(date(ts/1000,'unixepoch','localtime')) AS oldest,
       MAX(date(ts/1000,'unixepoch','localtime')) AS newest
FROM usage_records;
```
