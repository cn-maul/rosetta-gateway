# 管理面 HTTP 接口审计（2026-10-31）

React 迁移收尾后，趁人工走查前端的时间对后端接口做了一轮通读：**缺陷 / 可合并重复 /
性能**三个方向。本文记录审计方法、每条发现的判定与落地情况，以及**明确决定不做**的项
（附理由）—— 避免下一个人重开同一批讨论。

- 审计范围：`internal/api/api.go` 的 `routeSpecs`（112 个路由模式，含 5 条
  `/admin/api/` 方法兜底与 3 条 `/v1` 子树兜底）、对应 handler、`internal/store`
  查询层、`internal/access` 授权表、前端 `web/src` 的全部调用点与 57 个契约/纯函数测试。
- 方法：先读路由表建立端点清单，再按 6 条轴线并行只读审计（授权矩阵 / 重复端点 /
  HTTP 语义 / store 查询与索引 / 数据面公开端点 / 前后端契约），最后**每条都回源码
  逐字核实**才写进结论 —— 审计 agent 的推测一律降级为「待核」，除非能在代码里指出位置。
- 落地分支：`fix/api-audit-p0`，14 个提交，一条一提交，每条都先**证伪**（把修复还原，
  看测试变红）再恢复。

## 二、判定「不是 bug」，只更新注释或文档

- **`error.type` 两套词汇**（`auth_error` vs `invalid_request_error`）：`internal/server/authz_matrix_test.go`
  把 `auth_error` 当**契约**逐条断言，`key_policy.go` 也硬编码它。两套词区分的是「谁拒绝了
  你」——网关层（`UserAuth` / `AdminGateGuard`，经 `httpx.WriteAuthError`）在 handler 之前挡回，
  handler 内部（`requireAdmin` / `callerScope` 也算）用 `invalid_request_error`。统一成一种会让
  客户端分不清 403 的两种含义，因此**不改行为**，只在 `helpers.go` 写明分工。
- **`/admin/api/usage?group_by=` 与 summary 口径不同**：`group_byClause` 聚合的是 `usage_records`
  明细，summary 走 `store.UsageSource`（明细 + 归档）。这是该端点自身的边界 —— records 本就是
  明细（单次调用无法从日聚合还原），剪枝后 records 与分组行一起变少，与未分组时性质相同。
  它有专门的回归测试（`TestUsage_FractionalLatencyDoesNot500` 覆盖 `?group_by=key|model|day`）
  和一大段本地日界注释，删改都不划算。处理方式：注释里写明「要全区间按维度汇总请用 `/usage/by-*`」。
- **HTTP 语义「不标准」的地方都是刻意的**：创建一律 201、删除一律 200 + `{"status":"deleted"}`
  （无 204）、校验失败一律 400（无 422）、`Provider.Test`/`Balance` 恒 200（失败信息在 body）。
  前端按这套写，改动零收益。
- **`/dashboard/billing/usage` 用 PTM 口径**（tokens/1e6×100）：`DESIGN.md` 明确设计，不是错。
- **SQL 注入面为 0**：所有动态列名来自硬编码调用点，没有任何用户输入拼进 SQL。
- **`clampLimit` 默认 100 / 上限 1000、history 默认 200、CSV 超限写 `X-Export-Truncated`**：符合
  「大区间靠流式，不靠一次拉全」的既定策略。

## 三、刻意不做（附理由，别再重开）

- **`UpstreamModel` 不带 `provider_name`**，前端 `ModelGroups` / `PriceSettings` 因此多拉一次
  `/providers` 建查找表。收益是页面加载少一个请求（providers 列表本身很小且已被各页复用），
  代价是给 `/upstream-models` 与 `/model-groups/{id}/members` 加 join、改 DTO、重跑 contractgen、
  改三处前端。**性价比不足，不做**；真要省这一跳，更该做的是前端把 providers 结果放进共享
  store（与本次审计无关）。
- **读型数据面端点（`/v1/models`、`/dashboard/billing/*`）没有限流与窗口下界**：目前靠
  「只有持有有效 sk-gw key 才能打」这一层。加限流要先有按 key 的桶，属于配额体系的一部分
  （`AllowRPM` 现在只挂在补全流水线上），**留给配额体系一起做**，不在接口审计里硬塞。
- **`/admin/api/usage?group_by=` 不删**：理由见上一节（有测试、有注释、语义自洽）。
- **`userAccessibleRoutes` 精确表与 `routeSpecs` 两处维护**：`cmd/gateway/routes_test.go`
  已经用真实 `mux.Handler` 比对，漂移会立刻红；合并成一处等于把授权表塞进路由表，
  反而更难审。
