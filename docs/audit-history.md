## 第 4 轮为什么只审接口

前两轮是「全量读代码找问题」，代价是以十万行计的分析。第 4 轮的触发点是前端 React 迁移刚交付、
需要人工走查，于是趁这段时间只审**管理面 110 个 HTTP 端点**这一个切面：路由表、鉴权矩阵、
重复端点、HTTP 语义、查询计划、公开端点、前后端契约七个方向并行通读。产出精确到 `file:line`
与修法，且每条都先读源码核实再修（不采纳「拿 agent 报告直接改」的做法）。

## 补记：判定「不是 bug」与「刻意不做」的项

这些在原报告里都写了理由，此处只做索引，避免下一个人重开同一批讨论：

- 创建一律 201、删除一律 200 + `{"status":"deleted"}`（无 204）、参数校验一律 400（无 422）—— 全仓一致
- `Provider.Test` / `Provider.Balance` 恒 200（结果放在 body 里）—— 弹窗类交互的刻意语义
- `error.type` 有两套词：网关层拒绝用 `auth_error`，handler 内 scope 拒绝用 `invalid_request_error`
  —— 区分「谁拒绝了你」，`internal/server/authz_matrix_test.go` 已把它当契约钉住
- `/admin/api/usage?group_by=` 统计的是**明细表**，剪枝后不含已归档日期；要全区间请用 `/usage/by-*`
- 读型数据面端点（`/v1/models`、`/dashboard/billing/*`）不加 rate limit —— 待观察，不预防性加
- `UpstreamModel` 不补 `provider_name` —— 前端已有 provider 列表可映射，加字段会让 DTO 与缓存双重维护
