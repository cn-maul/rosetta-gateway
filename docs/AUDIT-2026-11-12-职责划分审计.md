## 0. 结论摘要

整体评价：**主干分工清晰，边界有测试保护；问题集中在“同一职责出现第二实现/第二口径”，以及文档落后于代码。**

值得肯定的部分（不是客套，而是审计中反复被证实的结构约束）：

- 生产路由只有一份注册来源 `internal/api/api.go`，测试与前端快照都从真实 `buildApp`
  导出，不靠手抄清单（`internal/api/api.go:59`、`cmd/gateway/route_contract_test.go:18`、
  `internal/server/authz_matrix_test.go:94`）。
- 架构依赖方向已写成机器门禁（`internal/architecture/imports_test.go:94`），
  `admin` 不得反向依赖 `server`、`store` 不得依赖上层等规则由 CI 兜底。
- 管理面鉴权收敛到单通道（users 表 + JWT），普通用户白名单用「方法 + 注册模式」
  精确匹配，默认 fail-closed（`internal/access/access.go:52`、`:117`）。
- 数据面请求骨架协议无关，三种下游协议经 `ingress.Codec` 注入
  （`internal/ingress/codec.go:18-31`），转发/流式/计费的公共路径只有一份。

需要处理的分工问题，按影响排序：

| 编号 | 问题 | 影响 | 建议优先级 |
|---|---|---|---|
| A1 | `admin` 包同时承担 HTTP 适配、查询编排与 SQL 拼装，统计查询已在包内另建一套 | 统计口径与 `store` 分叉风险；改表结构要改两处 | P1 |
| A2 | 单价公式放在 `store`，`billing` 只做估值适配与预检，`usage` 再经由 `store` 扣费 | “钱怎么算”缺少单一归属，包名承诺与实际职责不符 | P1 |
| A3 | 配置引导（`gatewayapp`）与配置导入（`admin`）是两套独立的图落库实现 | 校验/加密/幂等规则可能分叉，新增字段需改两处 | P2 |
| A4 | 运行期维护循环放在 `gatewayapp`，业务动作却在 `store`/`usage`/`probe` | 生命周期包承载了业务调度，测试与复用边界模糊 | P2 |
| A5 | `cmd/gateway` 为兼容测试保留了一套与 `gatewayapp` 重复的策略函数 | **已修复（2026-11-12）**：`billing.go` / `usage.go` / `routes.go` 删除，测试脚手架移入 `_test.go`；`balanceExempt` 降为 2 份（`gatewayapp` / `dataplane`，各读自己的快照入口） | 已关闭 |
| A6 | `catalog`、`billinghttp`、`probe` 直接复用 `outwire` 的错误封装 | 错误信封职责被多个入口共享，`outwire` 实际成为“协议公共层” | P3 |
| A7 | 管理员判定散落在 7 处（`store`、`auth`、`identity`、`access`、`admin`，以及 3 份 `balanceExempt`） | 一处收紧另一处不放宽时会出现口径差 | P3 |
| A8 | 文档与实现已明显脱节（导出范围、审计 actor、TS 版本、目录结构） | 会误导后续安全与架构判断 | P2 |
| A9 | 技术栈整体处于前沿区间，无落后大版本；但 `govulncheck` 报出 1 个标准库漏洞（Go 1.27.3，已在 1.27.4 修复） | 每个请求都套 `MaxBytesReader`，命中 GO-2026-6859 的适用形态，可致进程崩溃 | P1 |
| A10 | 先进性集中在数据面正确性；可观测性为零、target 级熔断不持久、测试依赖真实时间 | 复杂上游语义扛得住，但运维侧“看不见发生了什么” | P1（可观测性）/ P2（其余） |

```

                   runtime, server, snapshot, store, upstream, usage, userauth
```

关键观察：

1. `store` 是干净底层，只依赖 `dialect`/`effort`/`protocol` 三个纯值包，不依赖 HTTP 或运行时。
2. `admin` 不依赖 `server`（由架构测试强制），但**直接依赖 `snapshot` 全局单例**

   的规则形成不对称。
3. `api` 依赖 `admin`、`dataplane`、`catalog`、`billinghttp` 四个 HTTP 入口包，
   是唯一的装配层；`gatewayapp` 又反向依赖 `api` 取 handler，装配链是
   `gatewayapp → api → {admin, dataplane, ...}`，没有环。
4. `catalog` 依赖 `dataplane` 只为一个函数 `ModelNotFoundMessage`
   （import 在 `internal/catalog/models.go:12`，唯一调用在 `:106`），
   这让“公开模型目录”反向依赖“请求转发”。

## 2. A1：`admin` 的职责已经过宽

### 2.1 现象

`internal/admin` 名义上是“管理 API handlers”，实际承担了三层职责：

1. **HTTP 适配**：解码、鉴权后作用域、错误信封、审计字段。
2. **查询编排**：时间范围解析、分页、分组维度、CSV 导出。
3. **SQL 拼装**：直接把 `SELECT ... FROM usage_records` 写在 handler 里。

统计入口 `usage_handler.go` 有 1,323 行，其中 18 处 SELECT 语句（含子查询与 count 包装）；
`usage_failures_handler.go` 三处查询全部走 `h.store.DB()`（写池）：

```go
// internal/admin/usage_failures_handler.go:116
h.store.DB().QueryRowContext(...)
// internal/admin/usage_failures_handler.go:129
h.store.DB().QueryContext(...)
// internal/admin/usage_failures_handler.go:163
h.store.DB().QueryContext(...)
```

而 `store` 已经明确提供了读池：

```go
// internal/store/store.go:152-160
// DB 返回写池（管理面个别查询路径在用）。新代码请用 Reader。
func (s *Store) DB() *sql.DB { return s.db }
func (s *Store) Reader() *sql.DB { return s.read }
```

`usage_failures` 是纯读聚合，却走单连接写池，与“读写分池”的设计目标相反
（DESIGN §4 “读写分池”）。这不是正确性 bug，但会让一个重查询占用唯一写连接，
与用量落库、管理写、审计写排队。

### 2.2 为什么这是分工问题而不是风格问题

`store` 已经为用量统计提供了统一数据源与表达式：

- `store.UsageSource(filter)` 合并明细与日归档（`internal/store/usage_source.go:169`）；
- `store.UsageSumExpr` / `UsageRatioExpr` 保证明细与归档两分支列名一致；
- `GetUsageStats` 已经用这套表达式实现了总览统计（`internal/store/usage_dao.go:941`）。

但 `admin/usage_handler.go` 的 `summarize` 又手写了一套同样的聚合
（`internal/admin/usage_handler.go:404-430`），`GroupByUser` 又走
`store.UsageByUser`（`internal/store/usage_by_user_dao.go:75`）。
结果是同一个“区间总请求/总 token/失败数”存在至少两条实现路径：

- `/admin/api/stats` → `store.GetUsageStats`
- `/admin/api/usage` 的 `summary` → `admin.summarize` 手写 SQL

两者目前都调用 `UsageSource`，所以数字暂时一致；但**列名、过滤条件、失败判定**
各自维护。新增一个状态或改一次归档列，需要同时改两个包，而测试未必能覆盖
“两个入口给出同一答案”。

### 2.3 建议

把“用量查询”整体收进 `store`（或新建 `internal/usagequery`），`admin` 只做：

1. 解析 HTTP 参数（`from/to/limit/group_by`）；
2. 调 `store` 的查询方法；
3. 把结果映射成 DTO。

具体落点：

- `summarize` 改为 `store.GetUsageSummary(filter)`，与 `GetUsageStats` 共用同一组表达式；
- `usage_failures` 的三条查询移入 `store/usage_failures_dao.go`，并改用 `Reader()`；
- `ExportCSV` 与 `History` 的筛选条件已复用 `usageHistoryFilters`，但 SQL 仍在 handler，
  一并下移可消除“明细查询有两条实现”的现状。

不建议为了“分层好看”引入 repository 接口层；本项目单存储、单进程，
接口抽象会立刻变成无意义转发。**目标是单一实现，不是多一层接口。**

## 3. A2：单价公式的归属与包名不一致

### 3.1 现象

`internal/billing` 的包注释是“纯计价与余额预检策略”
（`internal/billing/billing.go:1`），但真正的价格公式在 `store`：

```go
// internal/store/pricing.go:116
// PriceUsage 是**全仓唯一的单价公式**
func PriceUsage(...)
// internal/store/pricing.go:209
func EstimateUpperBoundCost(...)
```

`billing` 一共只有 7 个函数（6 个导出 + 1 个内部辅助），且**没有一个自己实现单价公式**：

| 函数 | 实际内容 | 是否自有逻辑 |
|---|---|---|
| `EstimateBalanceCost` / `estimateBalanceCostWithInput`（`:65`、`:69`） | 取 `routing.UpstreamModel` 的四个价格字段装成 `store.Prices`，再调 `store.EstimateUpperBoundCost` | 只有“装字段 + 取 max_tokens”的适配 |
| `EstimateBalanceCostChain`（`:96`） | 遍历候选取最大值 | 编排 |
| `YuanToCents` / `CentsToYuan`（`:120`、`:123`） | 前者直接 `return store.YuanToCents(y)` | 纯转发 |
| `Preflight`（`:165`） | 比较估值与余额，返回 Reject/Allow | **自有**，这是真正的策略 |
| `ChainHasPricedModel`（`:196`） | 判断链上是否配了价 | 自有，但很短 |
| `IsBalanceExempt`（`:33`） | `role == store.RoleAdmin` | 自有，一行 |

所以更准确的描述是：**`billing` 不是空壳，但它的名字承诺了“计价”，
公式却全在 `store`；它实际提供的是“估值适配 + 预检判定”。**
`internal/store/pricing.go:116` 的注释“全仓唯一的单价公式”说明这个事实
已经被作者知道，只是包边界没有跟着调整。

也就是说，“价格怎么算”在 `store`，“要不要拒绝”在 `billing`，“扣多少钱”在
`usage → store.ChargeBalance`。三个包各自持有计费的一部分，没有一个包能独立回答
“这次调用收多少钱、为什么收这么多”。

### 3.2 影响

- 预检与实扣共用公式这一关键不变量，目前靠注释和测试维持，而不是靠包边界。
  `billing` 的注释明确说“审计前这里是手抄的第二份公式”（`internal/billing/billing.go:53-61`），
  说明历史上已经分叉过一次。
- `store` 作为“SQLite 访问层”承载了纯函数计价，导致 `billing` 必须依赖 `store`
  才能用价格类型；而 `usage` 只依赖 `store`（架构规则禁止 `billing` 反向依赖
  `usage`，`internal/architecture/imports_test.go:144-153`），扣费路径因此完全没有
  复用 `billing` 的 `Preflight` 判定，两套“够不够钱”的口径只能靠约定对齐。
- `billing.IsBalanceExempt(role string)` 直接引用 `store.RoleAdmin`，名为纯策略，
  实际绑定存储层常量。

### 3.3 建议

两种收敛方向，选其一即可，不要继续维持“公式在 store、策略在 billing、扣费在 usage”：

**方案 A（推荐，改动小）**：承认 `store` 是计价事实源，把 `billing` 改名为
`balance`（或 `billing` 保留名字但改注释），只保留“估值适配 + 预检判定”；
在包注释里写明“单价公式唯一实现在 `store/pricing.go`”，并让
`EstimateBalanceCost` 这类函数在文档里明确是“上界估算”，不是计价入口。

**方案 B（边界更干净）**：把 `pricing.go` 整体移到 `billing`，`store` 只负责
持久化已算好的 `cost_total`；`usage` 的扣费改为接收“已固化的金额”，不再调
`store.PriceUsage`。这样 `billing` 成为唯一计价包，`store` 回归 DAO。

方案 B 更符合包名，但要动 `usage` 的落库事务边界，风险高于收益；
若近期没有计费口径变更，建议先做方案 A 的“文档与导出面收敛”，把分叉面锁死。

## 4. A3：配置引导与配置导入是两套图落库

### 4.1 现象

同一件事——把“供应商 + 凭据 + 模型 + 路由 + 链首目标”写成一张完整的配置图——
存在两份实现：

1. 启动引导：`gatewayapp.bootstrapDB`
   （`internal/gatewayapp/bootstrap.go:19-166`）
2. 管理导入：`admin.ConfigTransferHandler.apply`
   （`internal/admin/config_transfer_handler.go:431`）及其
   `applyIdentities` / `applyRoutes`
   （`internal/admin/config_transfer_identities.go:33`、`:264`）

两者都做事务、都建 provider/credential/model/route/target，但规则不同：

| 维度 | 启动引导 | 管理导入 |
|---|---|---|
| 冲突处理 | 已有 provider 则拒绝启动或校验旧图 | slug 重名加 `-2` 后缀（只增不改） |
| 凭据 | `crypto.Encrypt` 直接加密（`internal/gatewayapp/bootstrap.go:97`） | 走 `encryptSecret`（`admin/helpers.go`），并校验主密钥 |
| 校验 | `config.validate()` 在加载阶段完成 | 导入时逐条校验，违例进 warnings |
| 幂等标记 | `MarkConfigBootstrapCompletedTx` | 无“完成标记”，每次导入都追加 |
| 网络 | 按 `proxy_url` 建网络 | 按网络名对齐，复用同名 |

这些差异**各自都有理由**（启动是“一次性建图”，导入是“跨库搬运”），
但实现上没有任何共享的“图写入器”。新增一个 provider 字段时，两处都要改；
漏一处的结果是“启动能建、导入丢字段”或反之。

### 4.2 已有测试的分工

- `internal/gatewayapp/bootstrap_graph_test.go` 覆盖启动图的原子性与完成标记；
- `internal/admin/config_transfer_*_test.go` 覆盖导入的干跑、重命名、凭据。

两边都测得很细，但**没有一条测试比对两者的字段覆盖**。这意味着分叉是静默的。

### 4.3 建议

抽一个最小的共享写入器，不追求“统一业务流程”，只统一**字段映射与加密**：

```go
// internal/configgraph（示例）
type ProviderSpec struct { ... }
func WriteProviderGraph(ctx, tx, spec, opts) error
```

启动引导与导入各自保留“冲突策略”，但都调用同一个 `WriteProviderGraph`。
这样新增字段只改一处，测试也只需钉住写入器的字段完整性。

若短期不做重构，至少加一条测试：用同一份配置分别走启动引导与导入，
断言落库后的 provider/model/route 字段逐项相等。

## 5. A4：维护循环放在生命周期包

### 5.1 现象

`gatewayapp/serve.go` 除了启动 HTTP 服务与优雅关停，还启动了四类业务维护循环：

| 循环 | 位置 | 业务归属 |
|---|---|---|
| 审计/用量/配额预占清理 | `startPruner`（`internal/gatewayapp/serve.go:166`） | `store` |
| 待重算费用 | `startRecompute`（`internal/gatewayapp/serve.go:256`） | `store` |
| 未扣费对账 | `startReconcile`（`internal/gatewayapp/serve.go:304`） | `store` + `usage` |
| 上游模型探测 | `startProbe`（`internal/gatewayapp/serve.go:347`） | `probe` |

每个循环内部都包含业务判定，例如：

- `startPruner` 里判断 `AuditLogKeepRows == 0 || < 0` 表示永久保留（`internal/gatewayapp/serve.go:182`）；
- `startReconcile` 直接调 `db.ReconcileUnchargedUsage(ctx, 500)`（`internal/gatewayapp/serve.go:318`），
  批量大小 500 是业务参数，不在配置里；
- `startProbe` 组装 `probe.NewRunner` 并管理其生命周期。

这导致 `gatewayapp` 同时是“进程生命周期 owner”和“后台任务调度器”。
`lifecycle` 包只提供 readiness/worker 计数，不提供调度能力。

### 5.2 影响

- 想单独测试“对账循环”必须构造完整的 `ServeDeps`，或者绕过它直接测 `store`；
- 维护循环的开关、周期、批量大小散落在 `serve.go` 与配置之间，没有单一视图；
- `gatewayapp` 的包注释说“owns the gateway's process lifecycle”，
  但实际代码远超生命周期。

### 5.3 建议

把四类循环收进一个 `internal/maintenance` 包（或各自的业务包提供 `Run(ctx)`）：

```go
// internal/maintenance
func Run(ctx, deps) // 统一注册 worker、统一日志、统一关停
```

`gatewayapp.Serve` 只负责：监听、HTTP server、信号、按顺序启动/停止 maintenance。
这样 `serve.go` 可以回到 200 行以内，维护循环也能独立测试。

## 8. A7：管理员判定的七处实现

当前至少七套“是不是管理员 / 是否免余额”的判定：

```go
// internal/store/user_dao.go:101
func (u *User) IsAdmin() bool { return u != nil && u.Role == RoleAdmin }

// internal/auth/auth.go:56
func (c *Context) IsAdminOwner() bool { ... u.Role == userRoleAdmin }

// internal/identity/identity.go:48
func IsAdmin(ctx context.Context) bool { u := UserFromContext(ctx); return u != nil && u.IsAdmin() }

// internal/admin/user_admin_handler.go:159
func requireAdmin(...) // 额外要求 ID 非空
```

`access.AdminGateGuard` 又自己写了一遍 `u.IsAdmin() && u.ID != ""`
（`internal/access/access.go:130`）。再加上两份 `balanceExempt`
（`internal/gatewayapp/run.go:389`、`internal/dataplane/balance.go:85`），
**“取角色 → 判 admin”这条链路现有 6 处实现**（`cmd` 那份已随 A5 删除）。

它们目前的语义差异是**有意的**：

- `store.User.IsAdmin()` 只看角色；
- `requireAdmin` 与 `AdminGateGuard` 额外要求 ID 非空（fail-closed）；
- `auth.IsAdminOwner` 用于数据面“管理员不能调模型”；
- `billing.IsBalanceExempt(role)` 只比较角色字符串，不碰 ID —— 这是
  “免余额”语义，与“能否进管理端”不同，**不应该**要求 ID 非空。

但“空 ID 不算管理员”这条规则在两处各写一次（`requireAdmin`、`AdminGateGuard`），
没有任何共享断言。
新增一个入口时很容易只写 `IsAdmin()`，从而引入 fail-open 的空 ID 通道。

建议在 `identity` 提供唯一判定，并按语义分两个名字，而不是一个函数包打天下：

```go
// 能进管理端：必须真有 ID，fail-closed。
func IsAdminUser(u *store.User) bool { return u != nil && u.IsAdmin() && u.ID != "" }
// 免余额：只看角色，保留 billing 现有语义。
func IsAdminRole(u *store.User) bool { return u != nil && u.IsAdmin() }
```

`access`、`admin.requireAdmin` 调用 `IsAdminUser`；`billing`、`dataplane`、
`gatewayapp`、`auth.IsAdminOwner` 调用 `IsAdminRole`。两份 `balanceExempt`
因此可以退化成一行，分叉面从 6 处降到 0 处。

优先级 P3：当前所有已知入口都做了正确判定，但没有机器约束防止未来回退。

- React 19 + React Aria 1.22 + HeroUI 3.2.7 属于同一代生态，没有 React 18 遗留。
- `go.mod` 只 require 3 个直接依赖，其余全是间接依赖。

### 13.2 可升级项（`go list -m -u` / `npm outdated` 实测）

| 组件 | 当前 | 最新 | 性质 | 建议 |
|---|---|---|---|---|
| `modernc.org/sqlite` | v1.61.1 | v1.62.0 | 次版本 | 可升，需跑全量测试（SQLite 行为变更风险低但非零） |
| `modernc.org/libc` | v1.79.0 | v1.81.0 | 间接依赖 | 随 sqlite 升级自动带上 |
| `golang.org/x/sys` | v0.49.0 | v0.50.0 | 间接依赖 | 跟随升级 |
| `golang.org/x/mod` / `x/sync` | v0.42.0 / v0.24.0 | v0.43.0 / v0.25.0 | 工具链依赖 | 不影响运行时 |
| `vite` | 8.3.6 | 8.3.8 | 补丁 | 可升 |
| `@vitejs/plugin-react` | 6.2.1 | 6.3.0 | 次版本 | 可升 |
| `lucide-react` | 1.70.0 | 1.72.0 | 次版本 | 可升 |
| `@typescript/typescript6` | 6.0.2 | 6.0.3 | 补丁 | 可升（与 TS 7 主版本无关） |

注意 `modernc.org/cc/v4`、`ccgo/v4` 等出现的“有新版本”**不是运行时依赖**。
用 `go mod why -m modernc.org/cc/v4` 实测，路径是
`internal/store → modernc.org/sqlite → modernc.org/libc → modernc.org/libc.test → modernc.org/cc/v4` ——
挂在 `libc` 的**测试**依赖上，生产构建不受影响，不必为它们单独排期。

**安全项（本次唯一必须做的一项）**：`govulncheck ./...` 实测报出

```text
GO-2026-6859 / CVE-2026-97054
HTTP/1 server crash due to MaxBytesReader header race in net/http
Found in: net/http@go1.27.3    Fixed in: net/http@go1.27.4
```

这是标准库 HTTP/1 服务的并发竞态：`MaxBytesReader` 在超限时于未加锁的情况下写入
`Connection: close`，若 handler 一边读 body 一边写响应头，可能触发 panic 使**整个进程崩溃**。
本项目的 `RequestSizeLimit` 中间件恰好对每个请求都套了 `MaxBytesReader`
（`internal/server/server.go:131`、`internal/api/api.go:560`），属于该漏洞的适用形态。

结论：**升级 Go 1.27.3 → 1.27.4 是本报告唯一“必须做”的版本动作**；其余升级都是
“顺手做”的量级，不是“必须做”。`npm audit --omit=dev`（走官方 registry）实测
`found 0 vulnerabilities`；默认 registry 是 npmmirror，它的 audit 端点是
`NOT_IMPLEMENTED`，所以 CI 里跑 audit 必须指定官方 registry，否则永远是空的。

### 13.3 依赖策略的取舍

项目有两处明确写在文档里的依赖纪律：

- 「零依赖」：路由用标准库 `net/http` 方法路由，配置用 `encoding/json`
  （`docs/DESIGN.md:1973`、`:1976`）。
- 限流刻意不用 `golang.org/x/time/rate`，理由是「零依赖是纪律」且令牌桶语义
  与运营直觉不符（`internal/ratelimit/limiter.go:12-15`）。

这个策略在**当前规模**下是合理的：3 个直接依赖、单二进制、`go:embed` 前端产物，
供应链面很小。它同时也是可观测性缺失（见 §14）的根因之一 —— 值得在升级时
重新评估，而不是无脑打破。

## 14. A10：架构先进性评估

### 14.1 已经领先或做得对的地方

这些不是“还行”，而是**明显高于同类网关项目平均水平**的设计：

1. **协议无关的数据面骨架**。`ingress.Codec` 只负责 decode / write error /
   write response / new sink 四件事，鉴权、限流、配额、故障转移、计费、看门狗
   全在 `dataplane.Handle`，新增一种下游协议不需要碰主循环
   （`internal/ingress/codec.go:18-31`）。
2. **快照整体替换 + `atomic.Pointer`**。没有 RWMutex 保护的大 map，没有
    “边读边改”的窗口，读路径是无锁的（`internal/snapshot/snapshot.go:238-261`）。
   配合 `AutoReload` 写后重建，配置生效路径也很短（`internal/api/api.go:239`）。
3. **流式写截止时间用 `http.ResponseController`**。这是 Go 1.20 才有的能力，
   项目用它解决“下游客户端不读导致写阻塞、上游继续计费”的泄漏，而且明确写了
   为什么不用“包一层 writer + goroutine”的替代方案（`internal/outwire/write_deadline.go:9-30`）。
   这类问题的正确处理在开源网关里并不常见。
4. **崩溃恢复语义被显式建模**。`committedKindFor` 把“已提交的流如何归因”
   收敛成一个判定点（`internal/dataplane/attempt_set.go:44-67`），
   计费用 `(request_id, user_id)` 占位行做幂等（`internal/store/balance_dao.go:491`）。
   这两条合起来，让“上游吐了一半断掉”不会变成重复扣费或漏计费。
5. **前端契约由 Go 生成，且有 CI 门禁**。路由快照、DTO 契约、默认值三份生成物
   都用 `git diff --exit-code` 守住（`.github/workflows/ci.yml:95-104`），
   这是很多前端项目做不到的。
6. **CI 有 `-race` 和“慢测”两轮**，并且注释里记录了“这一轮确实抓出过 DATA RACE”
   （`.github/workflows/ci.yml:161-164`、`:197-200`）。竞态检测不是摆设。
7. **前端状态管理刻意最小化**。自写约 25 行 `createStore` + `useSyncExternalStore`，
   不引 Redux/Zustand；全仓只有 `auth`、`session` 两个 store
   （`web/src/api.ts:48`、`:66`），其余状态都由组件本地 `useState` 承担。
   作者的理由写在 `web/src/store.ts:1-8`：“只有两个全局单例，多一层抽象
   就是多一份手写接线”。以这个应用规模，这是正确判断。
8. **供应链动作已 pin 到 commit SHA**，基础镜像 pin 到 digest
   （`.github/workflows/ci.yml:53`、`Dockerfile:22`）。

### 14.2 架构层面的真实短板

以下按“升级收益 / 改造成本”排序。

| 编号 | 短板 | 现状证据 | 升级方向 | 收益 | 成本 |
|---|---|---|---|---|---|
| B1 | **没有可观测性** | 全仓 0 处 OpenTelemetry / Prometheus / expvar / pprof 引用；只有 `/healthz` 与结构化日志 | 先加 `expvar`+`net/http/pprof`（零依赖）；再按需接 OTel metrics/trace | 线上问题从“看日志猜”变成“看指标定位” | 低（第一步）/ 中（OTel） |

| B8 | **没有 SCA / SBOM 门禁** | CI 有 `npm ci` 但没有 `govulncheck` / `npm audit` / SBOM 产物（本次手工跑出 1 个 stdlib 漏洞，见 13.2） | 加 `govulncheck ./...` + `npm audit --omit=dev --registry=https://registry.npmjs.org` + `syft` 生成 SBOM；Go 版本随 `go.mod` 单一来源自动升级 | 供应链风险可见，且能自动发现下一枚同类补丁 | 低 |
| B9 | **Node 版本没有单一来源** | CI 固定 `node-version: '22.12'`（`.github/workflows/ci.yml:223`），本机实测 Node 26.7.0；`web/package.json` 没有 `engines` 字段，Vite 8 要求 Node ^20.19.0 或 ≥22.12.0，这条约束只写在 CI 注释里。Go 侧已经做到 `go-version-file: go.mod` 单一来源，前端没有对应机制 | 在 `web/package.json` 加 `"engines": {"node": ">=22.12.0"}`，并把 CI 改为读 `.nvmrc`/`engines`；或至少让 `npm ci` 在版本不符时失败 | 消除“本地能跑、CI 挂”或反过来的类环境问题 | 低 |

### 14.3 关于 B4 的明确判断

这是本次评估里最容易被误判的一条。**单进程 + SQLite 不是技术债，而是产品定位。**

证据：

- `docs/DESIGN.md:42` 把“不做多节点集群”写成显式决策，不是遗漏。
- 数据面为此做了针对性优化：读写分池（`SetMaxOpenConns(1)` 写 + 4 读，
  `internal/store/store.go:59-71`）、WAL、`busy_timeout`。
- 熔断、限流、快照都是进程内状态 —— 如果改成多实例，这三样都要重做。

所以正确的升级方向不是“上集群”，而是**把单进程做到极致**：可观测性（B1）、
锁竞争（B2）、测试稳定性（B6）。如果将来真的需要多实例，应该作为一次
独立的架构迁移来评估，而不是零敲碎打。

## 15. A11：建议的升级路线

### 15.1 第一批（低风险、纯增益，建议直接做）

1. **升级 Go 1.27.3 → 1.27.4**（GO-2026-6859 / CVE-2026-97054，net/http
   `MaxBytesReader` 头部竞态可致进程 panic）。`go.mod` 的 `go` 行、
   `Dockerfile:22` 的构建镜像 digest 与 tag 都要一起改；CI 用
   `go-version-file: go.mod`，不需要改 workflow。这是本报告唯一的安全必做项。
2. **B1 第一步：加 `expvar` + `net/http/pprof`**。挂在管理面 mux 下、
   要求管理员身份，暴露 goroutine 数、堆大小、GC 次数、请求计数。
   零新依赖，半小时量级。
3. **B8：CI 加 `govulncheck ./...` 与 `npm audit --omit=dev`**。
   前者是官方工具，后者已随 npm 提供，都不引第三方 action。
   注意：本机默认 registry 是 npmmirror，其 audit 端点返回 `NOT_IMPLEMENTED`，
   CI 必须显式加 `--registry=https://registry.npmjs.org` 才有实际检查效果。
4. **依赖补丁升级**：`modernc.org/sqlite` v1.62.0、`vite` 8.3.8、
   `@vitejs/plugin-react` 6.3.0、`lucide-react` 1.72.0。跑一遍
   `go test ./internal/... -count=1` 与 `npm run typecheck && npm test` 即可。

### 15.2 第二批（需要小设计，收益明确）

5. **B6：用 `testing/synctest` 重写 `recorder_queue_test.go` 的时序用例**。
   这个文件用 4 处 `time.After`（行 80/101/112/134）+ 1 处 5ms 轮询（行 117）来等异步 worker，
   是“真实时间”依赖最集中的一处，改造收益最高。
6. **B3：把“单实例假设”写成代码注释/文档**（如果决定不做多实例）。
   目前只有 `DESIGN.md` 一句话，`Pool` 与 `ratelimit` 内部没有提示，
   后来者容易误以为可以加副本。
7. **B2：限流器先测再改**。作者在 `internal/ratelimit/limiter.go:21` 已经写了
   “单锁、微秒级、不值得分片”的判断，这个判断在当前规模下成立。
   要动它，先写 `go test -bench` 量锁竞争，再决定是否按 key 哈希分 shard。
8. **B9：给前端补 Node 版本单一来源**。`web/package.json` 加 `engines`，
   CI 从同一处读取，替代现在注释里的 “Vite 8 要求 ≥22.12”。

### 15.3 第三批（需要评估，不建议现在动）

9. **B1 第二步：OpenTelemetry**。只有在确实要接 Grafana/Jaeger 时再做；
   否则 `expvar` 已经够用，引 OTel 会打破“3 个直接依赖”的现状。
10. **B7：`encoding/json/v2` 试点**。先在 `inwire` 的非流式解码路径加 benchmark，
   有可测量收益再推广。
11. **多实例改造**。不建议，除非有明确的横向扩展需求。

### 15.4 一句话结论

**这套架构的“先进性”是真实的，但集中在数据面正确性（协议无关骨架、快照替换、
流式泄漏处理、幂等计费），而不是工程可运维性。** 它能扛住复杂的上游语义，
却几乎没有告诉运维“现在发生了什么”。最值得做的升级不是换技术，而是
补上可观测性 —— 这是投入产出比最高的一步。唯一的例外是安全：
`GO-2026-6859` 要求先把 Go 补到 1.27.4，这是一次补丁升级，不是架构调整。

## 16. 总体架构判断：合理，且有明确的下一层提升空间

### 16.1 一句话结论

**整体架构是合理的，而且不是“勉强合理”，是为当前产品定位（单机、单二进制、
SQLite、小团队）做过真实取舍的合理。** 数据面与控制面的分离、协议无关骨架、
不可变快照、生成式契约这四条主干都成立，并且有测试与 CI 门禁保护。

可以提升的地方**不在骨架，而在三处“体量追上来了但切分没跟上”的地方**：
控制面按文件横向铺开、数据面单函数过长、依赖注入一深一浅不对称。
这三处都不需要推翻重来，属于可以在一个迭代内完成的结构整理。

用一句话概括：**架构选型是对的，边界也是对的；问题在于边界内部的形状。**

### 16.2 支撑判断的量化证据

| 维度 | 实测 | 判断 |
|---|---|---|
| 包依赖方向 | `store` 只依赖 3 个纯值包；`admin` 不依赖 `server`；架构测试强制（`internal/architecture/imports_test.go:94`） | 健康。无环、无反向依赖 |
| 直接依赖数 | Go 侧仅 3 个（`go.mod:5-9`） | 优秀。供应链面极小 |
| 数据面协议扩展点 | 3 种下游协议共用 `Handle`，codec 只有 4 个方法（`internal/ingress/codec.go:18-31`） | 优秀。新增协议不改主循环 |
| 路由注册来源 | `internal/api/api.go` 单一 `routeSpecs`，121 条 pattern | 优秀。无第二份清单 |
| 契约门禁 | 路由 / DTO / 默认值三份生成物 CI `git diff --exit-code` | 优秀。同类项目少见 |
| 控制面体量 | `admin` 生产 11,688 行 / 27 个文件；最大单文件 `usage_handler.go` 1,323 行 | 需要整理。按资源切分，但每个资源内部仍是 handler+SQL+编排三层混合 |
| 数据面单函数 | `Handler.Handle` 从 `:183` 到 `:975`，约 790 行 | 需要整理。线性管道可读，但无法单独测试某一段 |
| 依赖注入 | `dataplane` 用 `SnapshotProvider` 注入（`internal/dataplane/handler.go:45`）；`admin` 有 9 处直接 `snapshot.Get()` 调用，分布在 6 个文件 | 不对称。`admin` 无法在测试里换快照 |
| 全局单例 | `snapshot.Get()` 调用在 `internal`+`cmd` 生产代码共 16 处（另有 1 处注释），分布在 5 个包 | 可控，但 `admin` 侧是隐藏依赖 |
| 测试形态 | `dataplane` 单包覆盖 20%，经 `cmd/gateway` e2e 达 75.6%；`store` 单包 63.4% | 金字塔“中段偏薄”。e2e 补上了覆盖，但反馈慢（22.8s） |
| 关停预算 | `lifecycle.ShutdownBudget` 单一来源，文档同步测试（`internal/lifecycle/budget_doc_test.go:20`），compose 写 31s | 优秀。这类一致性很少被机器守住 |
| 健康检查 | `HEALTHCHECK` 探 `/healthz`，会 ping 两个连接池并检查快照是否落后（`Dockerfile:80-91`） | 优秀。不是“进程活着就算健康” |

### 16.3 值得提升的三处（按收益排序）

#### 提升一：`admin` 按“资源”再切一层，把 SQL 挤回 `store`

现状不是“`admin` 太胖所以要拆包”，而是**同一个资源的三层职责写在同一批文件里**。
以 `usage_handler.go` 为例：HTTP 解码、时间范围解析、分页、SQL 拼装、CSV 序列化
五种东西在 1,323 行里交织，20 条 `SELECT` 直接写在 handler（本次统计）。

可落地的形状（不需要新框架）：

```text
internal/admin/usage/        # 只做 HTTP：参数解析、DTO、错误信封
internal/store/usage_query.go # 只做数据：过滤条件 → SQL → 行结构
```

判据很简单：**handler 里不再出现 `SELECT`**。达到这条，A1 的“两套统计口径”
就自动收敛了一半，因为两条入口会调用同一个 `store` 方法。

不建议做的是“给每个表建 repository 接口”。本项目单存储、单进程，
接口层会立刻退化成无意义转发 —— 报告 §2.3 已经写过这个判断，这里保持一致。

#### 提升二：把 `Handle` 的 790 行切成“可单独测试的阶段”

`Handle` 现在是**长但线性**：鉴权 → RPM → 解码 → 流准入 → TPM/配额预占 →
路由 → 尝试 → 记账。这个顺序本身是对的，问题是没有测试缝 ——
想验证“流准入超时后的配额回滚”必须把整条链路跑起来。

建议不是“按行数强拆”，而是**按已有的诊断阶段名切**。代码里已经用
`diag.begin("auth")` / `"decode"` / `"admission"` 标记了阶段
（`internal/dataplane/handler.go:211`、`:239`、`:265`），这套命名就是天然切分线：

```go
func (h *Handler) Handle(codec ingress.Codec) http.HandlerFunc {
    return func(w http.ResponseWriter, r *http.Request) {
        req, ok := h.admit(w, r, codec)   // 鉴权 + RPM + 解码 + 流准入
        if !ok { return }
        defer req.release()
        h.serve(w, r, req)                 // 预占 + 路由 + 尝试 + 记账
    }
}
```

这样每一段都能用假 codec + 假 pool 单独测，而 e2e 继续覆盖组合行为。
这是一次纯机械重构，行为不变，风险低，但收益是长期的。

#### 提升三：`admin` 的快照依赖改成注入，与 `dataplane` 对齐

`dataplane` 已经做对了：`SnapshotProvider func() *snapshot.Snapshot` 是构造参数，
测试可以塞任意快照（`internal/dataplane/handler.go:45`、`:61`）。
`admin` 却在 6 个文件里 9 次直接调 `snapshot.Get()`，包括读用户角色这种
安全相关判定（`internal/admin/key_handler.go:271`、`:849`、`:857`）。

后果不是当前有 bug，而是**`admin` 的测试必须操作全局单例**，无法并行、
无法构造“快照落后于数据库”的边界。把 `admin` 的 handler 基类加一个
`snap func() *snapshot.Snapshot` 字段（默认 `snapshot.Get`），改动面很小，
却能让 A7 的“管理员判定”真正可测。

### 16.4 明确不建议做的事

| 想法 | 为什么不做 |
|---|---|
| 引入 repository / service / domain 三层 | 单存储单进程，多一层就是多一次转发；现有包边界已经够表达依赖方向 |
| 拆成多服务（控制面 / 数据面分开部署） | 两者共享同一个 SQLite 与同一份内存快照；拆开要先解决状态共享，收益为负 |
| 把 `admin` 整体拆成多个 Go module | 编译期隔离带来的收益，远小于跨 module 改 DTO 的成本；`admin` 的耦合是“文件内”而不是“跨包” |
| 用 `golang.org/x/time/rate` 替换自研限流 | 作者已论证令牌桶语义与运营直觉不符（`internal/ratelimit/limiter.go:12-15`）；当前单锁成本可接受，先 benchmark 再谈 |
| 前端引入 Redux / Zustand | 只有两个全局单例，`useSyncExternalStore` 足够（`web/src/store.ts:1-8`）；引入状态库只会增加样板 |

### 16.5 如果只做一件事

**先做提升一（`admin` 的 SQL 下移）。** 理由：

- 它是唯一同时改善“职责边界”和“运行时行为”的一项 ——
  `usage_failures_handler.go` 三处查询现在走单连接写池（`:116`、`:129`、`:163`），
  改到 `store` 后顺带改用 `Reader()`，重查询不再和用量落库抢写连接。
- 它有明确的完成判据（handler 里没有 `SELECT`），不依赖主观判断。
- 它不触碰扣费事务，风险低于 A2 的计价归属调整。

提升二、三可以随后做，三者互不阻塞。
